### [R2-01] The roadmap's claim that T0.1 mechanically blocks Sprint 1 until Sprint 0 is done is false
Severity: HIGH · Confidence: Confirmed
**Affects:** T0.1, T0.2, T0.3, T0B.1, T0B.2, T1.1 (and every Sprint 1+ task)

**Evidence:**
- `project-harness/ROADMAP.md:139-141`: *"0. Sprint 0 first. The loop is not safe to run until
  Sprint 0 lands — see its header. T0.1 adds a preflight refusing to start outside a dedicated
  worktree, which is the mechanical block that enforces this."*
- T0.1's own spec (`ROADMAP.md:181-193`) only ever describes checking **which checkout** the
  loop runs in: *"Add a preflight that refuses to start in the primary checkout."* Nothing in
  its Spec, RED anchor, Validation or Done-when references T0.2, T0.3, T0B.1 or T0B.2's state.
- `scripts/_roadmap_cursor_core.py:16-18` (module docstring, verified by reading the file):
  *"Nothing outside the LOOP:QUEUE fence exists. 19 open tasks live elsewhere in the file
  (Phase PERF, Phase EVAL, …); the fence is what keeps them structurally unreachable at 3am."*
  Sprint 0 (T0.1–T0B.2) is explicitly outside the fence (`ROADMAP.md:132`: *"This sprint is
  deliberately OUTSIDE the LOOP:QUEUE fence"*). `compute_next` therefore cannot see whether
  T0.2/T0.3/T0B.1/T0B.2 are ticked — the fence design the roadmap itself relies on for safety
  (keeping stray sections unreachable) is the same mechanism that makes Sprint-0 completeness
  invisible to the cursor.
- `scripts/expand_loop.sh`'s current `preflight()` (`:168-220`) contains no worktree check and
  no reference to Sprint 0 at all — confirming T0.1 has not landed and, once it does, the
  preflight it describes checks location only, never task completeness.

**Why it breaks the programme:** the roadmap advertises a single mechanical gate for a real
safety property ("do not run the loop until Sprint 0's fixes are in") but the gate it names
only enforces "run from a worktree." An operator who creates a worktree the moment T0.1 lands
and starts the loop satisfies the preflight while T0.2 (stale-lock recovery), T0.3 (harness
self-test HALT routing) and, most importantly, T0B.1 (the stale "144s gate duration" /
"300-line limit" claims) are still unfixed. T0B.1's own spec calls the 144s claim "the
night-losing one" (scar 6.1) precisely because an agent told to expect 144s and seeing nothing
concludes the gate hung — and that exact failure mode is left fully armed by a preflight that
only checks the working directory. The written instruction "do not start until Sprint 0 is
done" is real but purely a human-followed convention; nothing in the code enforces it.

**Proposed fix:** either (a) have T0.1's preflight also grep the raw roadmap file (outside the
fence, since the script is allowed to read the whole file — only `compute_next`'s task
selection is fence-scoped) for `- [ ] **T0.2**` / `T0.3` / `T0B.1` / `T0B.2` and refuse to start
if any remain unchecked, or (b) rewrite `ROADMAP.md:139-141` to stop calling this a "mechanical
block" and state plainly that only the worktree half is enforced in code — the rest is
operator discipline, and the risk of skipping it is the specific defects T0.2/T0.3/T0B.1 exist
to fix.

### [R2-02] Sprint 7's demo census cannot tell "load-bearing test for a surviving module" from "dead code," and can delete the tests T5.1/T5.2 just added
Severity: HIGH · Confidence: Likely
**Affects:** T13.1, T13.2, T5.1, T5.2

**Evidence:**
- T13.1's method (`ROADMAP.md:1043-1046`): *"Run the scripted demo to completion … and the
  interactive walkthrough … and record which modules are actually imported and executed. Use
  `coverage run` over the demo process rather than reading imports statically — a
  statically-imported module that never executes is exactly what you are hunting."* The output
  is one table: *"module, executed in scripted run, executed in walkthrough, verdict
  keep/delete."*
- T13.2's Files line (`ROADMAP.md:1061`) is `demo_game/, e2e/, project-harness/ISSUES.md` —
  unrestricted, and explicitly includes `demo_game/tests/` (confirmed present:
  `demo_game/tests/` holds 87 test files across `beats/`, `core/`, `pollers/`, `scenarios/`,
  `seeds/`, `ui/`). T13.2's own batching guidance names "pollers, panels, branches, scenarios,
  runners" as the subsystems to cut — it never names `tests/` as a category to exclude, nor
  does it say tests should be judged by a different rule than the coverage-during-a-live-run
  method T13.1 just established.
- No test file is ever imported or executed by the demo **process** — tests run under pytest,
  a separate process from the one T13.1 instruments with `coverage run`. Applying T13.1's stated
  method literally to `demo_game/tests/**/*.py` returns "not executed in scripted run, not
  executed in walkthrough" for **every** test file in the tree, including
  `demo_game/tests/seeds/test_seed_schedules.py` and `test_seed_needs.py` that T5.1/T5.2 (Sprint
  3, four sprints earlier) were required to add.
- The one safety net, T13.2's RED anchor (`ROADMAP.md:1082-1084`): *"`make test-demo` before and
  after — baseline 1,116 passed. The count must drop by exactly the tests belonging to deleted
  modules; any other delta means something load-bearing went."* This check is tautological for
  this failure mode: if the T5.1/T5.2 test files are themselves the "deleted modules," the drop
  matches the deleted set by construction. It verifies internal arithmetic, not that a still-live
  module (`demo_game/seeds/seed.py`, which nothing else in the programme proposes removing)
  keeps its regression coverage.

**Why it breaks the programme:** this is the exact failure the review's own "How it was built"
warning describes happening one sprint removed — Sprint 3 does real, tested work (T5.1/T5.2),
and Sprint 7's own census methodology, applied as written, has no way to protect that work from
being swept up four sprints later under the same "not executed live, therefore dead" logic that
correctly kills a stale poller. `demo_game/tests/pollers/test_treaty_poller.py` (confirmed to
exist) is a good example of a *legitimate* deletion candidate the same table would produce
alongside the false positive — nothing in the spec distinguishes them.

**Proposed fix:** add one sentence to T13.1's spec: "Judge `demo_game/tests/` by whether the
module it tests is kept, not by whether the test file itself executed during a live run —
compute the census over `demo_game/` **excluding** `tests/`, then separately map each surviving
test file to the module(s) it imports; a test importing only survivors is kept regardless of its
own coverage." Change T13.2's RED anchor to also assert, by name, that
`demo_game/tests/seeds/test_seed_schedules.py` and `test_seed_needs.py` (and any other test
whose target module survives) are present after the trim, not just that the aggregate count
balances.

### [R2-03] T6.2's own evidence file names two read-after-write pairs that no longer exist by the time T6.2 runs
Severity: MEDIUM · Confidence: Confirmed
**Affects:** T6.2, T3.2, T4.1

**Evidence:** T6.2 (`ROADMAP.md:571-585`, Sprint 3 / Phase T6) instructs: *"targeted tests for
each read-after-write pair in L13.md section A.2, asserting the writer's index is lower than the
reader's."* Reading `project-harness/review-fixes/evidence/L13.md:44-57` (section A.2) directly,
the table has 12 rows. Two of them:
- `mood_contagion (11)` reads co-location, written by `routine (4)` — `mood_contagion` is deleted
  by T4.1 (Sprint 2, Phase T4), two phases before T6.2 runs.
- `faction_politics (6)` reads `:Event` rows, written by `gossip (2)` / `event (3)` —
  `faction_politics` is deleted by T3.2 (Sprint 2, Phase T3), one phase before T6.2 runs.

Neither engine exists in the tree by the time T6.2 executes. T6.2 does not say "skip pairs whose
engines Sprint 2 removed" — it says "each read-after-write pair," full stop, and separately
instructs *"pin the order as it is *now**"* only for the full-sequence assertion (a), not for the
per-pair assertions in (b).

**Why it breaks the programme:** an agent following T6.2 literally has 2 of 12 required
sub-assertions written against classes that no longer exist. A careless implementation would try
to import `MoodContagionEngine`/`FactionPoliticsEngine` in the new test, fail at collection, and
red `make check` for a reason unrelated to the actual ordering work; a careful one has to notice
the mismatch and silently drop two of the "required" pairs with no instruction telling it that is
correct. This is exactly the transcription-drift risk the review spec calls out: the L13.md
table is frozen evidence from before Sprint 2's own deletions were decided, and nothing
downstream re-validates it against the sprint that runs before it.

**Proposed fix:** add to T6.2's spec: "Two of L13.md §A.2's twelve pairs (`mood_contagion`
reading `routine`, `faction_politics` reading `gossip`/`event`) name engines Sprint 2 already
deleted — skip them; ten pairs remain to test."

### [R2-04] T6.3's live-tail runs need_quest_trigger unbounded, in the exact window Sprint 4 exists to close
Severity: HIGH · Confidence: Likely
**Affects:** T6.3, T5.2, T7.1, T7.2

**Evidence:**
- T5.2's own sequencing note (`ROADMAP.md:566-568`): *"this revives `need_quest_trigger`, which
  **increases** the quest-generation LLM amplification that Sprint 4 exists to bound. That is
  acceptable because Sprint 4 follows immediately; do not reorder the two sprints."*
- Between T5.2 and Sprint 4 (T7.1), the only loop-run tasks are T6.1, T6.2, and the deferred
  T6.3. `make test-demo` (`Makefile:822-823`) is `pytest demo_game/tests/ -q` — no live stack,
  no real Ollama calls — so the *automated* loop path genuinely never exercises the
  amplification between T5.2 and T7.1, which is what makes the "acceptable" claim true for
  unattended nights.
- T6.3 itself (`ROADMAP.md:590-609`) is the one task in that window that **does** run live:
  *"Bring a stack up, advance the clock several ticks against the seeded world, then read
  `GET /v1/admin/system/engines` and assert `routine` reports a non-zero `moved` count and
  `need_decay` reports a non-zero worked count."* By construction this is the first live tick
  advance to run after `HAS_NEED` edges exist (T5.2) and before T7.1's shared per-tick LLM
  budget lands — precisely the unbounded window T7 exists to close, and T6.3 is a **deferred**
  (pause-glyph) task meant to be picked up by a human as soon as it's reached, not after Sprint
  4 has landed weeks later.
- T7.2's own worst-case figures (`ROADMAP.md:743-746`): *"need triggers 10 x up to 4 [calls] …
  84 for a saturated tick"* — a per-tick load T6.3's "advance the clock several ticks" would
  reproduce against a single resident model with no admission control (T8.1 also not yet
  landed) and a 10s per-call timeout (`LLM_TIMEOUT_SECONDS`, config default, per T8.2's spec).

**Why it breaks the programme:** T6.3's own Done-when clause is a hard binary: *"If either is
still zero after T5.1 and T5.2 landed, do not tick this task — the seed edit did not achieve its
purpose and the defect is upstream."* If the unbounded trigger load causes calls to time out or
queue behind each other during T6.3's tick advance, `need_quest_trigger`'s reported count can
read as zero (or flaky) for load reasons that have nothing to do with whether T5.2's seed fix
worked — exactly the ambiguity Sprint 4 exists to remove. An operator hitting that would, per
the task's own instruction, conclude Sprint 3 failed and start "fixing" a defect that isn't
there.

**Proposed fix:** either move T6.3 to run after T7.1+T7.2 land (accepting that Sprint 3's
confirmation is delayed, which the roadmap already tolerates for other pause-glyph tasks), or
add an explicit caveat to T6.3's spec: "advance ticks one at a time and watch for LLM timeouts in
the log; a zero or flaky `need_quest_trigger` count under visible timeout errors is a Sprint-4
ordering artifact, not evidence T5.2 failed — do not use it to reopen Sprint 3."

### [R2-05] T4.2's engine-census exempt list omits `engines/emotion/`, which declares no tick engine and isn't in either exempt list
Severity: MEDIUM · Confidence: Confirmed
**Affects:** T4.2

**Evidence:**
- T4.2 (`ROADMAP.md:529-535`) partitions `src/npc_engine/engines/*` into three buckets: (1)
  dirs wired into `TickScheduler` (checked mechanically); (2) named non-tick engines — *"dialogue,
  economy, interaction, quest, relationship, knowledge_learning, idempotency"* — exempt from (1)
  but must be imported from `api/routes/`; (3) named infra dirs — *"ports/, contracts/, llm/,
  tts/"* — exempt entirely.
- `grep -rn "run_tick" src/npc_engine/engines/emotion/*.py` returns nothing — `emotion/` declares
  no `TickEngine` and is wired into no scheduler slot. It is not in bucket (1).
- `emotion` is not among the seven names in bucket (2), and not among the four in bucket (3).
- `emotion/` **is** imported from `src/npc_engine/api/routes/dialogue/npc_state.py` (confirmed by
  `grep -rln "engines.emotion" src/npc_engine/api/routes/`), so it is live, load-bearing code —
  just uncategorized by the roadmap's three named buckets.

**Why it breaks the programme:** `check_engine_census.py` is specified against exactly these
three buckets. Implemented literally, a directory that is neither wired nor named in either
exempt list has no defined outcome — most likely it is treated as a violation of rule (a)/(b)
("must be wired or imported by routes... [wait, it IS imported, so if the script's third-bucket
default falls through to the route-import check anyway it would pass — but the spec never says
that's the fallback]"), so the gate's behavior here depends on an implementation detail nobody
wrote down. T4.2's own RED anchor requires the gate to "report zero" on the current, post-Sprint-2
tree; if the implementer's fallback treats an unlisted directory as a failure, T4.2 reds on its
own Done-when criterion at first run over a live, correctly-used module — a false positive in the
exact gate meant to stop dead-code regrowth.

**Proposed fix:** add `emotion` to T4.2's non-tick-engine list: *"dialogue, economy, interaction,
quest, relationship, knowledge_learning, idempotency, emotion."* Also instruct the script to
fail loudly (not silently pass or silently fail) on any directory matching none of the three
buckets, so a future addition is a conscious edit rather than an ambiguous default.
