## Part 2 — the deterministic question

Judged against the gossip precedent (`src/npc_engine/engines/gossip/` — "Deterministic
NPC-to-NPC rumor propagation with personality/faction-weighted pair selection and distortion",
`gossip/__init__.py:3-4`, no model call anywhere in the package):

| Call site | Convert to deterministic? | Reasoning |
|---|---|---|
| #1 chapter labeling | **No — but shrink.** The fallback (`label_chapter_by_rules`) already exists and runs on every failure. It is not proven equivalent in quality, but chapter titles/themes are exactly the kind of short creative-labeling task a rule table can approximate; DEC-059 already accepts a rule-based fallback path as good enough to ship. Converting the *primary* path is a product-quality call outside this lens's evidence — kept **needs 7B/3B**, not deterministic, but flagged as the weakest "needs a model" claim in the table. |
| #2/#3 dialogue generation | **No.** `npc_response` is unbounded in-character prose responding to arbitrary player text — this is open generation with no fixed output set. Not a determinism candidate. |
| #4 memory consolidation | **No.** Free-text summarization of variable-length turn logs into a memory description has no fixed template; genuinely needs generation. (Separately: it is called via the *wrong* protocol method — `generate`, not `generate_structured` — for a task that returns JSON. See L11-04.) |
| #5 proactive line | **No, but bounded already.** One in-character ambient line responding to a specific memory/need/event — open generation, but low-stakes (dropped silently on failure) and already capped at 1 call/tick. |
| #6 quest slot-filling | **YES — convert to deterministic.** The schema is `additionalProperties: string` filled from a **candidate list already fetched from the graph** (`_get_candidates`, `quest_generation_engine.py:151+`). This is picking N items from a small enumerated set per slot — the exact shape of a classification-over-a-fixed-set task the review brief names as the delete-by-determinism bar. The code **already has** `_deterministic_fill` as the retry-exhaustion fallback (`quest_generation_engine.py:236`) — it is proven code, already shipping, already exercised on every 4th call in practice (retry exhaustion). Converting slot-filling to always use `_deterministic_fill` (optionally RNG-seeded per `_quest_rng_seed`, which the engine already derives) removes 3 of the 4 model calls in the pipeline with **no new code**, only deletion of the LLM path and its retry loop. What is lost: whatever correlation the model adds between giver context (mood/needs/goals) and slot choice beyond what `_deterministic_fill`'s RNG selection provides — today that correlation is already discarded on any retry-exhaustion (silently reverts to the same RNG path), so the "loss" is bounded by how often the LLM path currently produces a *better* fill than RNG selection over the same candidate pool, which nothing in the eval stack can currently measure (all judged scorers are refused). |
| #7 quest flavor text | **No.** Free-text description + NPC plea grounded in giver context — open generation, not a fixed-set pick. The template-default fallback already used on failure (`template.description_template`) is a plausible but bland substitute — a legitimate case for **needs 7B/3B**, not for deletion. |
| #8-10 quest triggers | Inherit #6 (deterministic) + #7 (needs model) verdicts; the volume problem (Part 3) is a stronger argument for cutting #6's retries specifically at these call sites, since a background tick has no player watching if a slot pick came from the RNG path already used on every retry-exhaustion. |

**Net:** of 10 call sites, 1 cluster (slot-filling, reached from 4 call sites: #6, and inside
#8/#9/#10) is a clean delete-by-determinism candidate with a working, shipping, already-executed
fallback. That alone removes up to 30 of the 40 worst-case model calls in the quest-trigger
amplification case in Part 3 below (3 of 4 calls per invocation are the retried slot-fill).

## Part 3 — reliability and amplification

### Retry amplification — worst case per action

**One interactive dialogue turn:** 1–2 model calls (`_generate_with_retry`, 2 attempts max).
At 3.5–4.2s decode-dominated per warm call (DEC-273), a full retry exhaustion is ~7–8.4s
sequential — already past the 3-7s budget's upper bound on a single retry.

**One interactive quest-generation request** (`POST /v1/quest/generate`): up to
**3 (slot-fill retries) + 1 (flavor) = 4 sequential model calls**, none `wait_for`-wrapped at
the route (`quest_generation.py:99` has no timeout wrapper visible; the route relies solely on
the global 10.0s per-call `httpx` timeout). Worst case ≈ 4 × 10.0s client timeout ceiling before
the route can even *fail* cleanly, or 4 × ~3.5-4.2s ≈ 14-17s if every call succeeds slowly — either
way, multiples of the 3-7s dialogue budget, on a route with no documented budget of its own.

**One background tick, worst case (all three quest triggers plus proactive fire):**

| Trigger | Cap/tick | Calls/invocation | Worst-case calls |
|---|---|---|---|
| `event_quest_trigger` | `_MAX_EVENTS_PER_TICK = 10` | up to 4 | **40** |
| `need_quest_trigger` | `_MAX_NEEDS_PER_TICK = 10` | up to 4 | **40** |
| `world_state_quest_trigger` | `DEFAULT_MAX_PER_TICK = 1` | up to 4 | **4** |
| `proactive_dialogue` | 1 winner/tick (`proactive_tick_adapter.py`) | 1 | **1** |
| `chapter` | 1/tick (rare — chapter-open condition) | 1 | **1** |
| `memory_consolidation` | 1 call per NPC crossing the turn threshold, no per-tick cap found in `memory_consolidation_engine.py` | 1 | **unbounded by NPC count** |

**Worst-case total ≈ 86 sequential model calls in a single tick** (40+40+4+1+1, excluding the
uncapped memory-consolidation term), all funneled through ONE resident `qwen2.5:7b` on ONE GPU
(DEC-273: only one model fits in 12 GB VRAM; co-residency evicts). Ollama serializes generation
requests against a single loaded model — it does not run them in parallel on one GPU. At ~3.5-4.2s
decode per warm structured call, 86 sequential calls is **5-6 minutes of continuous decode**
monopolizing the only LLM backend in the process. Engine ticks run sequentially within
`_run_tick_body` (confirmed: each `await engine.run_tick(...)` completes before the next starts —
no `asyncio.gather` across engines), so this is not concurrent GPU contention *within* the tick,
but it is wall-clock contention *against* any interactive dialogue request arriving during those
5-6 minutes: that request's HTTP call queues behind whichever quest-trigger call is mid-decode,
and DEC-273's 3.5-4.2s warm dialogue figure assumes an otherwise-idle backend. This is exactly the
"3-attempt structured-output loop on a background tick competing with an interactive dialogue turn
on ONE resident model" scenario named in the brief, quantified: **worst case, one tick can make a
player's dialogue turn wait minutes, not seconds, behind a queue of quest-generation retries.**

The partial existing mitigation — `skip_llm_engines` (`tick_scheduler.py:467,535`, wired through
`tick_autopilot.py:98`) — gates only `chapter` and `memory_consolidation`. It does **not** gate
any of the three quest triggers or proactive_dialogue, i.e. it misses the two highest-amplification
call sites (event/need triggers, 80 of the 86 worst-case calls) entirely.

### [L11-01] `stream`/`stream_text` call site is dead in the production dialogue path
Severity: MEDIUM · Confidence: Confirmed
**Evidence:** `dialogue/dialogue_handler.py:371-390` defines `DialogueHandler.stream()`, which
calls `self._llm.stream_text(...)` (→ `llm_client.py:237` → `OllamaAdapter.stream`,
`ollama_adapter.py:222`). `grep -rn "handler\.stream(\|dialogue_handler\.stream" src/npc_engine
--include=*.py"` (excluding tests) returns zero rows. The WS route
(`api/routes/dialogue/dialogue_ws.py:198-199`) calls `handler.handle()` (the non-streaming path)
and re-chops the finished string with `_iter_token_chunks` (`dialogue_ws.py:124`) instead — DEC-273
documents this explicitly ("the WS route already fakes it").
**Why it matters:** Three of ten call sites in this table (`stream`/`stream_text` in the adapter,
client, and handler) exist for a code path nothing in production reaches. It is exercised by unit
tests only. This is dead surface carrying its own retry-free, timeout-bearing HTTP logic
(`ollama_adapter.py:222-291`) that must still be kept in sync with the non-streaming path's
behavior (fallback text, metric labels) with no runtime check that it has not drifted.
**Fix sketch:** Either wire the WS route to real token streaming (DEC-273 explains why this was
rejected — `_apply_output_ceiling` needs the complete response before any token can be considered
safe to ship) or delete `DialogueHandler.stream()` and `DialogueLLMClient.stream_text()` and drop
`LLMStreamProtocol` down to the two backends that still need `stream()` for something else (none,
today — `LLMClientProtocol` composes it unconditionally). Log the removal as a DECISIONS.md entry
per project rules (interface change with only-test callers still counts as a public interface).

### [L11-02] Per-engine declared timeouts are dead configuration for 4 of 5 engines
Severity: HIGH · Confidence: Confirmed
**Already known:** ISSUE-298 (temperature version of the same defect — this finding generalizes
it to `timeouts_ms`, which ISSUE-298 does not mention).
**Evidence:** `grep -rn "timeouts_ms" src/npc_engine --include="*.py"` returns exactly two
non-model rows: the Pydantic model field (`engines/llm_config_models.py:96`) and its only reader,
`dialogue_handler.py:248-249`. `chapter/llm_config.yaml:16`, `memory_consolidation/llm_config.yaml:16`,
`proactive_dialogue/llm_config.yaml:16-17`, and `quest_generation/llm_config.yaml:16-17` all declare
`timeouts_ms.full` (30000/30000/20000/30000ms respectively) that **no code path reads**. The actual
enforced ceiling for all five engines' underlying HTTP call is one process-wide value,
`settings.LLM_TIMEOUT_SECONDS` (default `10.0`, `config.py:111`), passed to every `OllamaAdapter`
constructor uniformly (`factory.py:88,103`) regardless of which engine it serves.
**Why it matters:** An engineer reading `quest_generation/llm_config.yaml` and setting
`timeouts_ms.full: 30000` to give quest generation more headroom changes nothing — the call still
dies at 10s. Conversely, dialogue's declared 200000ms tier timeout (`degradation.py:124`,
genuinely enforced via `asyncio.wait_for`) is itself gated behind the same 10s HTTP timeout one
layer down, so the 200s figure is asserted, not reachable — the HTTP layer throws
`LLMTimeoutError` at 10s long before `wait_for` would ever fire at 200s. This is the "asserted,
not measured" pattern the 2026-06-03 review named systemically (`_CONTEXT.md` pattern #2),
recurring here for timeouts specifically.
**Fix sketch:** Either (a) thread `EngineModelConfig.timeouts_ms.full` into
`create_llm_client_for_engine` as the per-adapter `timeout_seconds`, deleting
`settings.LLM_TIMEOUT_SECONDS` as a cross-engine default, or (b) delete the `timeouts_ms` field
from the four engines that do not use it and document that only dialogue has tiered timeouts.
(a) is more honest to the YAML's apparent intent; (b) is smaller and matches what ships today.

### [L11-03] Quest-generation triggers can multiply into 40+ sequential model calls per tick with no cap shared across the three trigger engines
Severity: CRITICAL · Confidence: Confirmed
**Evidence:** `event_quest_trigger.py:32` (`_MAX_EVENTS_PER_TICK = 10`) and
`need_quest_trigger.py:24` (`_MAX_NEEDS_PER_TICK = 10`), each invocation running
`_fill_slots`'s up-to-3-attempt loop (`quest_generation_engine.py:218-236`) plus one
`_generate_flavor` call (`quest_generation_engine.py:295-319`) — up to 4 calls per invocation,
up to 40 per trigger per tick, up to ~84 across both plus `world_state_quest_trigger.py:34`
(1 invocation × 4 calls). See Part 3 table above for the full worst-case derivation.
**Why it matters:** This is the single largest latency-amplification surface in the engine
portfolio. It runs on a scheduler tick — no player action gates it — against the same single
resident model an interactive dialogue turn needs, with the two highest-volume triggers entirely
unprotected by the one load-shedding switch that exists (`skip_llm_engines`).
**Fix sketch:** Two independent levers, either sufficient alone: (1) apply the Part 2 verdict —
delete the LLM path from slot-filling (`_ask_llm_for_fills`), always using
`_deterministic_fill`, cutting the per-invocation ceiling from 4 calls to 1 (flavor only) and the
tick-worst-case from ~84 to ~21; (2) extend `skip_llm_engines` (or a new, more granular flag) to
gate all three quest triggers, not just chapter/memory_consolidation.

### [L11-04] Memory consolidation asks for structured JSON through the unstructured `generate` protocol
Severity: MEDIUM · Confidence: Confirmed
**Evidence:** `memory_consolidation_engine.py:131-137` calls `self._llm_client.generate(...)`
(plain text) and the caller does `json.loads` on nothing in this file — checking further, unlike
`chapter_engine.py:257-261` (`generate` → `json.loads(raw.strip())`), the memory-consolidation
prompt template (`prompts/memory_consolidation/consolidation_v1.yaml`, referenced via
`_PROMPT_PATH`) is not schema-constrained by `generate_structured`'s `format` field
(`ollama_adapter.py:154-220`), so there is no grammar constraining the model's output shape at
all for this call site — worth flagging alongside chapter (#1), which has the identical pattern
(`generate` + manual `json.loads`, `chapter_engine.py:257-263`) and is a CR-L02-05-adjacent
instance of "no raw dict crossing a boundary" (that finding was about `LLMClientProtocol
.generate_structured()` specifically; this is the same defect one protocol tier down, on
`generate`, which has no schema field at all to violate — the violation here is *not using*
`generate_structured` where a structured contract is intended).
**Already known:** CR-L02-05 (`grep` confirms in `review-2026-08/FINDINGS.md:96`) covers
`generate_structured()`'s dict typing; does not cover engines that use plain `generate` for
what is actually a structured extraction task. New ground.
**Why it matters:** Without a schema constraint, `qwen2.5:7b` (or a smaller model) must both
generate correct JSON syntax *and* the content in one unconstrained decode — no `format` field
in the Ollama payload (`ollama_adapter.py:118-132`) means no grammar-guided decoding, which is
strictly more room for malformed output than the schema-fenced sibling call sites (dialogue,
quest generation) get for free.
**Fix sketch:** Convert `memory_consolidation_engine.py`'s and `chapter_engine.py`'s calls from
`generate` to `generate_structured` with a small explicit schema (memory summary /
title+description+theme respectively). Both already hand-parse JSON from a free-text response;
switching protocols removes that hand-parsing and gets grammar-constrained decoding for the same
token budget.

### [L11-05] Proactive dialogue line generation has zero fallback and zero declared-timeout enforcement
Severity: MEDIUM · Confidence: Confirmed
**Evidence:** `proactive_engine.py:205-210` — no `try/except` around
`self._llm.generate(...)`. Compare chapter (`chapter_engine.py:255` — bare `except Exception`)
and memory_consolidation (`memory_consolidation_engine.py:132` — bare `except Exception`), both
of which self-protect at the call site. Proactive relies entirely on
`tick_scheduler._run_engine_safe` (`tick_scheduler.py:238-243`) catching the exception one layer
up, which it does — so this is not a crash risk — but it means `ProactiveDialogueEngine` cannot
be reused (called directly, outside the tick scheduler's safety net) without inheriting an
unguarded LLM call, violating the module's own claim to be "safe for concurrent use" in isolation.
**Why it matters:** `proactive_engine.py:38-39` also hardcodes `_MAX_TOKENS = 128` and
`_TEMPERATURE = 0.8` as module constants that happen to numerically match
`proactive_dialogue/llm_config.yaml:6-7` today but are not read from it (ISSUE-298 already names
this exact file/lines) — so both the model's generation parameters and its failure handling are
disconnected from the engine's own declared config and from the safety pattern used by every
sibling engine.
**Fix sketch:** Add the same `try/except (LLMTimeoutError, LLMRequestError)` at the call site with
a `None`-returning or logged-skip fallback, matching chapter/memory_consolidation's local
self-protection instead of relying solely on the tick scheduler's catch-all.

## What survives a 3B

| Call site | Verdict | Why |
|---|---|---|
| #1 chapter labeling | **needs 7B** (weak) | Open generation, but a working deterministic fallback already exists and is unproven-worse; borderline — a 3B is plausibly adequate given the fallback safety net, but nothing in the usable eval stack can confirm quality at either size |
| #2/#3 dialogue `npc_response` text | **needs 7B** | Unbounded in-character prose responding to arbitrary player input — the one call site where model capability most directly reaches the player |
| #2 dialogue structured fields (deltas/mood/action/expression) | **survives 3B** | Small closed-vocabulary extraction riding alongside #2's prose in the same call — not separable today, but the *demand* is 3B-shaped even though the *call* isn't |
| #4 memory consolidation | **needs 7B** | Free-text summarization with no fixed template; also currently unschematized (L11-04), so quality depends more on the model's own JSON discipline than a 3B may have |
| #5 proactive line | **survives 3B** | Short (128 tokens), low-stakes (dropped silently on failure), one line of ambient flavor |
| #6 quest slot-filling | **should be deterministic** | Picking from an already-graph-fetched candidate list; the deterministic fallback is proven, shipping code exercised on every retry-exhaustion today |
| #7 quest flavor text | **needs 7B** | Grounded open-generation prose (description + NPC plea); template-default fallback is visibly blander |
| #8-10 quest triggers | inherits #6 (deterministic) + #7 (needs 7B) | The volume problem is a determinism/frequency argument, not a capability one |
| stream/stream_text (#3, dead) | **n/a — delete** | Not reachable in production; the question does not apply |

**If `qwen2.5:7b` were swapped for a 3B tomorrow:** the classification/extraction halves of
call sites #2, #5, and #6 would very likely hold — small closed-vocabulary or candidate-list
picking is exactly what a 3B is built for, and #6 already has a deterministic escape hatch that
makes the swap risk-free there regardless of model size. What breaks is open generation quality:
dialogue's `npc_response` prose (#2), chapter titles (#1), and quest flavor text (#7) would need
re-validation nothing in the current eval stack can perform (all five judged scorers are REFUSED
by the adequacy floor — DEC in `_CONTEXT.md`), so "breaks" here means *unverifiable*, not
*provably worse*. Two things would have to happen before the swap is safe to ship, independent of
model size: (1) fix the label-adequacy gate so at least one judged scorer is trustworthy again —
right now there is no instrument in the repo that could tell a 3B's dialogue quality apart from a
7B's — and (2) fix L11-02 (dead per-engine timeouts) so a 3B's presumably faster decode doesn't
mask a still-present config/enforcement mismatch that would resurface the moment someone tunes
`timeouts_ms` expecting it to do something.

**The single highest-leverage change:** delete the LLM call from quest slot-filling
(`_ask_llm_for_fills`, call sites #6/#8/#9/#10) and always use the existing, already-shipping
`_deterministic_fill`. This is not a latency optimization in the DEC-273 sense (fewer tokens
out, fewer calls, smaller model) applied to one call — it is the second of those three levers,
**fewer calls**, applied at its highest-multiplier point: it removes up to 30 of the ~86
worst-case sequential model calls in a single tick with zero new code, because the fallback this
finding proposes making universal is the exact code path retry-exhaustion already runs today.
