## Findings

### L4-01: arm_probe.py and arm_probe_report.py, the P9 measurement-integrity tool, ship at 0 percent coverage; its HTTP client is 46 percent

Severity: HIGH. Confidence: Confirmed.

Evidence: measured live (pytest tests/unit/evals/ tests/unit/scripts/ -q --cov=evals --cov-report=term-missing):
evals/arm_probe.py: 77 statements, 0 covered, 0 percent, lines 23-167.
evals/arm_probe_client.py: 39 statements, 21 covered, 46 percent, missing 58-64, 87-88, 94, 97, 100, 123-128, 132-134, 138-142.
evals/arm_probe_report.py: 37 statements, 0 covered, 0 percent, lines 15-116.
arm_probe.py's own docstring calls it "the thing standing between an operator and a ten-hour null result", but _run, _live_gates, _observe_all, _finish, and main (its gate-ordering, exit-code, and --gate selection logic) have no test at all. arm_probe_client.py's ProbeClient.observe, including the ValueError raised when the debug route returns no receipt (arm_probe_client.py:58-64, documented as "a cached assembly publishes none") and the HTTPStatusError path for an undeclared arm, is untested; only the happy path is exercised transitively via test_arm_probe_gates.py's fakes. arm_probe_report.py's print_observations (the added/removed key diffing and _spend formatting) has zero coverage. This contrasts with the other Phase-5 files landed in the same commit (ef870f7f): probe_dialogue.py, probe_events.py, probe_gossip.py, prelabel_runner.py, adjudication_yield.py all sit at 96-100 percent.

Already known: none found in ISSUES.md, archive/ISSUES_RESOLVED.md, or review-2026-08/FINDINGS.md and TRIAGE.md; arm_probe* postdates the 2026-08-28 baseline (landed in ef870f7f).

Why it matters: the standing goal is measurement integrity for a small local model; this tool exists specifically to stop a ten-hour generation run being spent on an arm that never reached the model differently. A bug in _run's gate-ordering or in ProbeClient.observe's error handling would only be caught by a human reading console output during a live run, the exact failure mode the tool's own docstring says it exists to prevent.

Fix sketch: unit-test _finish's exit-code logic and _live_gates's --gate selection against a fake ProbeClient (the pattern test_arm_probe_gates.py's _FakeClient already establishes); test ProbeClient.observe's ValueError/HTTPStatusError paths against a stub transport; test print_observations's added/removed diff against two fixed ArmObservations.

### L4-02: Auth-middleware wiring on the production app has no regression test; only a hand-built app is verified

Severity: HIGH. Confidence: Confirmed.

Evidence: src/npc_engine/main.py:271-278 wires ApiKeyMiddleware into create_app(). The only test that exercises ApiKeyMiddleware end-to-end against a live 401 (tests/unit/api/test_dialogue_pending_route.py:45-56,110-119) builds its own FastAPI() instance (_build_app, line 45) with one router mounted and the middleware added conditionally, never create_app(). Every test that does call create_app() (tests/unit/conformance/test_boot_smoke.py:36-60, test_v1_route_versioning.py, test_route_response_model_contract.py, test_typed_payload_contract.py, test_graph_v13_routes.py) checks route registration, response models, or /health's 200, none sends an unauthenticated request to a protected route on the real app object and asserts 401. tests/unit/api/test_auth_permissions_v13.py:4 states outright: "Does NOT: exercise full HTTP middleware pipeline."

Already known: not found in ISSUES.md, archive/ISSUES_RESOLVED.md, or review-2026-08.

Why it matters: "auth on every route except GET /health" is a rule project-harness/CLAUDE.md states in full, not a pointer elsewhere, the project's own definition of what must never regress silently. If app.add_middleware(ApiKeyMiddleware, ...) were ever removed from main.py:274-278, no unit test in the suite would go red; only a live/e2e run would notice, matching the review brief's systemic pattern of live-only breaks staying unguarded.

Fix sketch: add a test that calls the real create_app() (as test_boot_smoke.py already does), sends an unauthenticated GET to a known protected route (for example /v1/dialogue/pending), and asserts 401, mirroring test_returns_401_without_auth_header but against the production app object instead of a hand-assembled one.

### L4-03: make check executes zero real Cypher; the gap already produced a live, invisible red test (ISSUE-274)

Severity: HIGH. Confidence: Confirmed. Already known: CR-L14-02 (PARTIAL, see re-verification table).

Evidence: Makefile:432 (the check target list) does not include check-integration-baseline; test-cov and test-cov-evals run plain pytest tests/, which, measured live with no NEO4J_URI set, collects 51 integration tests and executes only 11, skipping 40 (pytest tests/integration -q gave "11 passed, 40 skipped"). CI's full-gate job (.github/workflows/ci.yml:8-34) runs make check with no Neo4j service, so it inherits this same skip pattern; the separately-added integration-tests job is a distinct job, not a check prerequisite, and whether it is required for merge is undetermined locally (branch protection is a GitHub setting; already flagged as unknown in review-2026-08's CR-L06-06). project-harness/ISSUES.md:374-401 (ISSUE-274, found 2026-09-03, five days after the 2026-08-28 baseline) records exactly this failure mode live: test_quest_lifecycle_offer_to_completion_and_rewards fails in 0.35s on a test-construction defect (QuestLifecycleEngine requires a TypeRegistry injected), and the issue's own text says make check without services collects and skips the integration suite so it reads green while this test is red, and that it only surfaced because the loop was launched with --with-services.

Why it matters: the standing invariant this violates is CLAUDE.md's own testing rule, "Neo4j-touching code gets integration tests against a real test DB", read together with the pre-merge checklist that names make check. The tests exist and are well-written (for example the tick-isolation coverage confirmed above), but the local/default invocation of the project's own completion gate never runs them against real data. This already cost real time (ISSUE-274).

Fix sketch: ISSUE-274's own "To fix" covers the specific test defect. At the process level: either add check-integration-baseline to check when NEO4J_URI is set and default the loop to --with-services, or have the MIN_EXECUTED_TESTS floor fail loudly rather than skip silently when invoked without services, so a make check run without Neo4j is visibly incomplete rather than quietly green.

### L4-04: WS connection-cap enforcement is untested at the endpoint; only the internal helper is exercised

Severity: MEDIUM. Confidence: Confirmed.

Evidence: src/npc_engine/api/routes/dialogue/dialogue_ws.py:221-225 is the only call site that turns _acquire_ws_slot's return value into a rejected connection (websocket.close(code=1008)). The only test on this mechanism, tests/unit/conformance/test_sev20_auth_surface.py:126-142 (test_acquire_ws_slot_enforces_cap_and_releases), calls dialogue_ws._acquire_ws_slot directly; it never calls the dialogue_ws endpoint function or opens a TestClient websocket. tests/unit/api/test_dialogue_ws_route.py covers only _build_done_data; the other two WS test files cover unrelated helpers. If lines 221-225 were deleted (the connection accepted unconditionally, _acquire_ws_slot left orphaned but present), every existing test would stay green.

Already known: this is the residual half of the 2026-06-03 review's L1-01 ("WS cap defined but never enforced"), which HOLDS AS FIXED for the enforcement logic itself (re-verified above), but the wiring that connects the fixed logic to the actual endpoint remains exactly as unprotected as before, one layer down.

Why it matters: the cap exists specifically to stop unmetered per-frame LLM amplification (the module's own docstring). A refactor of the endpoint (for example reordering the accept() and cap-check lines) would silently remove the protection with no CI signal.

Fix sketch: add a TestClient(app).websocket_connect(...) test that opens MAX_WS_CONNECTIONS_PER_KEY connections for one key and asserts the next one closes with code 1008, the same class of fix as L4-02 applied to the WS route.
