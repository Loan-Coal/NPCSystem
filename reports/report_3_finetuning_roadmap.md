**System prompt** (verbatim from `prompt_builder.py:14–46`):

```
You are a non-player character (NPC) in a medieval fantasy RPG world. You receive a JSON CONTEXT and a PLAYER_MESSAGE and must reply with a JSON object matching the required schema.

BEHAVIORAL RULES — apply ALL of them every turn:

1. WORLD STATE — read `context.world.epoch`:
   - "age_of_peace": calm world, normal commerce and travel
   - "war": active conflict nearby — you are tense, wary, roads are dangerous
   - "famine", "plague", etc.: reflect the hardship in tone and available resources
   Also read `context.world.active_conditions` (list of ongoing events you would know about).

2. PLAYER REPUTATION — read `context.player_reputation` (list of faction standings):
   - allied   (standing 50–100): warm, eager to help, may share secrets
   - friendly  (standing 20–49): cooperative, pleasant
   - neutral   (standing -19–19): polite but guarded
   - unfriendly (standing -20 to -49): cold, clipped, may refuse requests
   - hostile   (standing -50 to -100): contemptuous or threatening, will NOT help
   If the list is empty, treat the player as a stranger (neutral).

3. NPC EMOTION — read `context.npc.emotion.current_mood` and let it color your sentence structure and word choice.

4. PERSONA — your name, archetype, and personality traits are in `context.npc.profile`. Stay true to them at all times.

5. KNOWN EVENTS — `context.npc_known_events` lists what you know. Do NOT invent facts absent from this list.

6. CONVERSATION HISTORY — `context.recent_session_turns` shows prior exchanges. Stay consistent with what you already said.

Output rules:
- `npc_response`: 1–3 sentences of in-character speech. Tone MUST reflect reputation and world state.
- Do NOT break character, mention JSON, or reference game mechanics.
- Do NOT repeat the player's message verbatim.
```

**User prompt template** (verbatim from `prompt_builder.py:65–71`):

```
PROMPT_VERSION=stage_b_v1.0
NPC_ID={request.npc_id}
PLAYER_ID={request.player_id}
CONTEXT={serialized_context}
PLAYER_MESSAGE={request.player_message}
```

`{serialized_context}` is a compact JSON string (`context_serializer.serialize_context`):

```json
{
  "world": {"epoch": "...", "active_conditions": [...]},
  "npc": {"profile": {...}, "emotion": {"current_mood": "..."}},
  "player_reputation": [{"faction_name": "...", "standing": -80, "label": "hostile"}],
  "player_relation": {...},
  "npc_known_events": [...],
  "nearby_npcs": [...],
  "recent_session_turns": ["...", "..."]
}
```

**Output schema** (`DialogueResponse` in `dialogue_models.py:57–68`):

```json
{
  "npc_response": "Aldric eyes you carefully. 'I've nothing to say to the likes of you. Move along.'",
  "relation_deltas": {"trust": -5, "fear": 0, "affection": -3},
  "mood_update": "suspicious",
  "action": {"type": "speak", "target_id": null, "parameters": {}},
  "facial_expression": {"type": "frown", "intensity": 60}
}
```

Constraints:
- `relation_deltas.{trust,fear,affection}`: integer in `[-15, 15]`
- `action.type`: `Literal["speak","gesture","move","attack","give_item","buy_item","sell_item","none"]`
- `facial_expression.type`: `Literal["neutral","smile","frown","angry","surprised","sad"]`
- `facial_expression.intensity`: integer in `[0, 100]`
- `session_id`, `cached`, `degradation_level` are appended after parsing — **not generated by the LLM, exclude from training labels**

**Variable vs. fixed content:**
- **Fixed**: entire system prompt, prompt skeleton keys (`PROMPT_VERSION=`, `NPC_ID=`, etc.)
- **Variable**: `npc_id`, `player_id`, full `CONTEXT` JSON (world, NPC profile, emotion, reputation, events, session turns), `player_message`

| Param | Value |
|---|---|
| model | mixtral:8x7b |
| temperature | 0.8 (streaming only — NOT forwarded to `generate_structured`) |
| max_tokens | 512 |
| top_p | 0.95 |
| stop_sequences | `[]` |
| prompt budget (input) | 800 tokens |
| full-tier timeout | 60000 ms |

**Important nuance**: `generate_structured` at `llm_client.py:85–92` passes `max_tokens`, `top_p`, `stop_sequences`, `system` — temperature is NOT forwarded. Fine-tune for structured-output behavior, not sampled completion.

## Section 2: Training Data Collection

### 2.1 Where to Hook

The cleanest interception layer is a **decorator adapter** around `LLMClientProtocol` — wrap whichever concrete adapter is injected via `dependency_singletons.py`. The decorator delegates all calls to the real adapter and writes a JSONL log entry. This captures all three engines uniformly, requires zero engine code changes, and survives prompt-version bumps (the full prompt string is captured verbatim).

| Engine | Call site | Method intercepted |
|---|---|---|
| Dialogue | `engines/dialogue/llm_client.py:85` | `generate_structured` |
| Quest slot-fill | `engines/quest_generation/quest_generation_engine.py:205` | `generate_structured` |
| Quest flavor | `engines/quest_generation/quest_generation_engine.py:239` | `generate_structured` |
| Memory consolidation | `engines/memory_consolidation/memory_consolidation_engine.py:104` | `generate` |

### 2.2 What to Capture

Per row in the JSONL log:

```json
{
  "timestamp": "2026-05-13T14:22:18.331Z",
  "request_id": "<uuid generated by wrapper>",
  "engine": "dialogue | quest_slot_fill | quest_flavor | memory_consolidation",
  "model_name": "<adapter.model_name()>",
  "prompt_version": "stage_b_v1.0 | slot_fill_v1 | flavor_v1 | consolidation_v1",
  "system": "<full system string or null>",
  "prompt": "<full user prompt string>",
  "schema": "<json schema dict or null>",
  "raw_response": "<dict or string — pre-validation>",
  "parsed_response": "<dict or string — post-validation>",
  "validation_error": "<pydantic error message or null>",
  "latency_ms": 1234,
  "max_tokens": 512,
  "top_p": 0.95,
  "stop_sequences": [],
  "npc_id": "<from request, dialogue only>",
  "player_id": "<from request, dialogue only>",
  "session_id": "<from request, dialogue only>",
  "degradation_level": "full | graph_only | canned | null"
}
```

### 2.3 Quality Signal (Offline Filtering)

Do not gate the hook on quality — capture everything, filter offline.

**Dialogue** — include if ALL of:
- `validation_error is None` (JSON parseable + schema-valid)
- `degradation_level == "full"` (produced by LLM, not canned fallback)
- `relation_deltas` all in `[-15, 15]`
- `len(npc_response.split()) >= 3`
- `player_message` is not a verbatim substring of `npc_response`
- Optional: LLM judge "is this in character given the archetype?" returns YES

**Quest slot-fill** — include if ALL of:
- `SlotValidator.validate(...)` returned `[]` (no violations)
- All required slots are filled
- The call did NOT fall back to `_deterministic_fill` (add a `succeeded: bool` flag in the wrapper)

**Quest flavor** — include if ALL of:
- Both `description` and `npc_plea` present in parsed output
- `description` mentions at least one fill value or `giver_name` (name-grounding check)
- `len(description.split()) >= 20`

**Memory consolidation** — include if ALL of:
- Output non-empty after `.strip()`
- Contains first-person pronouns (`"I "` or `"my "`)
- Mentions at least one named character from the input turns
- Passes the existing LLM judge rubric from `e2e/scenarios/scenario_llm_judge.py:140–146`

### 2.4 Volume Estimates

| Engine | Minimum viable | Comfortable | Production quality |
|---|---|---|---|
| Dialogue (structured JSON + persona) | 1,000 | 3,000–5,000 | 10,000+ |
| Quest slot-fill (constrained selection) | 300 | 800–1,500 | 3,000 |
| Quest flavor (creative JSON) | 500 | 1,500–2,500 | 5,000 |
| Memory consolidation (summarization) | 300 | 800–1,500 | 3,000 |

Dialogue needs the most because it has the largest output schema (5 nested fields), the largest variable input (the full CONTEXT JSON), and the strongest persona-consistency demand. Quest slot-fill is near-classification (the model selects from an explicit list) and converges fast. Uncertainty band: ±50%; validate empirically with a pilot at 500/1000/2000 examples and watch the JSON parse rate curve.

### 2.5 Data Augmentation

**Dialogue**
- **Teacher distillation**: run Mixtral-8x7B (or a cloud model with the same system prompt) over procedurally generated (CONTEXT, player_message) pairs from seeded graph states.
- **Reputation sweep**: hold archetype + message fixed, vary reputation across all five bands → 5x examples per seed, directly teaches the reputation→tone mapping.
- **World-state sweep**: hold all else fixed, vary `world.epoch` across `age_of_peace`, `war`, `famine`, `plague` → 4x multiplier.
- **Negative samples**: include canned fallback responses from `degradation.py` as DPO/ORPO "rejected" examples if you move to preference tuning.

**Quest slot-fill**
- **Graph permutation**: for each template, generate N graphs with different valid candidate sets and capture teacher outputs.
- **Violation curriculum**: include retry-step examples (`violation_context` non-empty) — teaches recovery from bad first attempts, matching the production retry loop at `quest_generation_engine.py:163`.

**Quest flavor**
- **Slot-paraphrase**: same fills, multiple outputs from teacher at different temperatures → stylistic diversity.
- **Giver-name conditioning**: vary `giver_name` to reinforce name-grounding behavior.

**Memory consolidation**
- **Turn-length curriculum**: synthesize sessions of 5, 10, 20, 40 turns to handle variable input lengths.
- **Multi-character sessions**: sessions where multiple NPC names appear — teaches name preservation.

## Section 3: Fine-Tuning Approach

### 3.1 Recommended Base Models

| Engine | Recommended | Rationale |
|---|---|---|
| Dialogue | **Mistral-7B-Instruct-v0.3** | Native JSON-mode, strong roleplay, 32k context, Apache 2.0 |
| Quest slot-fill | **Phi-3.5-mini-instruct (3.8B)** | Constrained selection task — 3B is sufficient, 2x faster to train; strong JSON conformance |
| Quest flavor | **Mistral-7B-Instruct-v0.3** | Needs creative prose + JSON — Mistral's narrative fluency wins over Phi here |
| Memory consolidation | **Mistral-7B-Instruct-v0.3** | Summarization is a pre-training strength; consistent with dialogue base |

**Strong recommendation**: standardize on **Mistral-7B-Instruct-v0.3** across all engines for the first iteration → one base + three LoRA adapters → VRAM stays constant (see Section 5.4). Phi-3.5 for quest_slot_fill is a second-pass optimization once you have a baseline.

### 3.2 Training Format

All engines: **ChatML / ShareGPT format** with explicit `system` / `user` / `assistant` roles. Unsloth has first-class support; this matches the runtime call (adapters pass `system` separately). Train on assistant tokens only — use Unsloth's `train_on_responses_only` utility.

**Dialogue example:**

```json

  "conversations": [
    {"from": "system", "value": "You are a non-player character (NPC) in a medieval fantasy RPG world... [full system prompt verbatim]"},
```

### 3.3 LoRA Configuration

| Engine | r | lora_alpha | lora_dropout | target_modules | bias |
|---|---|---|---|---|---|
| Dialogue | 16 | 32 | 0.05 | `q_proj, k_proj, v_proj, o_proj, gate_proj, up_proj, down_proj` | `"none"` |
| Quest slot-fill | 8 | 16 | 0.0 | `q_proj, k_proj, v_proj, o_proj` only | `"none"` |
| Quest flavor | 16 | 32 | 0.05 | full set (same as dialogue) | `"none"` |
| Memory consolidation | 16 | 32 | 0.05 | full set | `"none"` |

Rationale: `r=16, alpha=32` is the Unsloth community default for 7B instruction tuning (`alpha = 2r` keeps effective LR scale stable). Dialogue uses MLP layers too because persona-conditional output requires more capacity than attention-only. Quest slot-fill is near-classification — attention-only `r=8` is sufficient and trains 2x faster. `dropout=0.0` for small datasets (<500 examples); `0.05` otherwise.

For Phi-3.5-mini, target modules are `qkv_proj, o_proj, gate_up_proj, down_proj` (fused QKV and gate_up).

### 3.4 Unsloth-Specific Considerations

- **4-bit base loading**: `FastLanguageModel.from_pretrained(model_name="unsloth/mistral-7b-instruct-v0.3-bnb-4bit", load_in_4bit=True)` — cuts VRAM ~4x.
- **Max sequence length** (set at load time, pre-allocates RoPE cache):
  - Dialogue: `max_seq_length=2048` (800-token prompt + 43-line system + 512 output ≈ 1.4–1.6k; round up)
  - Quest slot-fill: `1024`
  - Quest flavor: `1024`
  - Memory consolidation: `2048` (40-turn sessions can exceed 1k input tokens)
- **Gradient checkpointing**: `use_gradient_checkpointing="unsloth"` — saves ~30% VRAM with minimal speed loss. Enable for all.
- **Flash Attention 2**: enabled by default on Ampere+ (RTX 3090/4090 both qualify). No action needed.
- **Packing**: `packing=True` is efficient for quest_slot_fill (short examples). Disable for dialogue and memory_consolidation — variable lengths can blur EOS boundaries on the assistant turn.

### 3.5 Training Recipe

| Hyperparameter | Dialogue / Flavor / Memory | Quest slot-fill |
|---|---|---|
| epochs | 3 (start; tune 2–5) | 3–4 |
| per_device_train_batch_size | 2 | 4 |
| gradient_accumulation_steps | 8 (effective batch = 16) | 4 (effective batch = 16) |
| learning_rate | 2e-4 | 2e-4 |
| lr_scheduler_type | cosine | cosine |
| warmup_ratio | 0.03 | 0.03 |
| optim | adamw_8bit | adamw_8bit |
| weight_decay | 0.01 | 0.01 |
| max_grad_norm | 1.0 | 1.0 |
| seed | 3407 | 3407 |
| eval_strategy | steps, every 50 | steps, every 50 |

For 1000 examples × 3 epochs × effective batch 16 ≈ 190 optimizer steps. Eval at 50/100/150/180. Early-stop on eval loss plateau.

## Section 4: Evaluation Strategy

### 4.1 Held-Out Test Set

80% train / 10% val / 10% test with stratified sampling:
- **Dialogue**: stratify by `(archetype, world.epoch, reputation_band)` triplet. ~60 strata; ensure every stratum has ≥1 test example.
- **Quest slot-fill / flavor**: stratify by `template_id`. Every template must have ≥3 test examples.
- **Memory consolidation**: stratify by `turn_count` buckets (5–9, 10–19, 20+) and `archetype`.

For production data collected after the first training run, use a **time-forward holdout** (later timestamps) to detect distribution drift.

### 4.2 Automatic Metrics

**Dialogue**

| Metric | Target |
|---|---|
| JSON parse rate | ≥99% |
| Pydantic schema validation rate | ≥98% |
| Delta bounds compliance (`[-15, 15]`) | 100% |
| Action/expression enum compliance | 100% |
| Response length (1–3 sentences) | ≥95% |
| Verbatim-echo rate (player_message in npc_response) | <1% |
| Tone classifier accuracy (archetype × reputation_band) | ≥80% |

**Quest slot-fill**

| Metric | Target |
|---|---|
| Graph validation pass rate (first try, no retries) | ≥95% |
| Required-slot coverage | 100% |
| Node-type accuracy | ≥98% |

**Quest flavor**

| Metric | Target |
|---|---|
| JSON parse + required fields present | ≥99% |
| Name-grounding score (giver_name or fill value in description) | ≥80% |
| Description length (30–200 words) | ≥95% |

**Memory consolidation**

| Metric | Target |
|---|---|
| ROUGE-L vs. session content | ≥0.25 |
| Character name preservation | ≥90% |
| First-person rate | ≥95% |
| No JSON / no bullets in output | 100% |

### 4.3 LLM-as-Judge Prompts

Reuse the existing `e2e/helpers/llm_judge.py` YES/NO scaffold. Run each criterion as a separate independent call (Likert aggregation is noisier for small models).

**Dialogue** (pass if ≥4/5 YES):

```
1. "Does this NPC response stay true to the archetype '{archetype}'?"
2. "Does the tone match the player's reputation band '{reputation_band}'?"
3. "Does the response avoid breaking character or referencing game mechanics?"
4. "Does the response avoid repeating the player's message verbatim?"
5. "Does the response acknowledge the world state '{epoch}' if relevant?"
```

**Quest flavor** (pass if ≥3/3 YES):

```
1. "Does the description coherently reference the quest target and location?"
2. "Does the npc_plea sound like in-character speech from a quest giver?"
3. "Is the description free of meta-references (no 'the player', no 'the quest')?"
```

**Memory consolidation** — use the existing rubric from `scenario_llm_judge.py:140–146`:

```
Does this text read as a coherent first-person memory or observation from an NPC who has been gathering evidence and speaking carefully with a player? It should feel like a personal recollection, not a list of bullet points or a summary template.
```

**Important**: the judge model must differ from the model under evaluation. Use Mixtral-8x7B or a cloud API as the judge; use the fine-tuned Mistral-7B as the system under test.

### 4.4 Regression Testing

- **E2E golden regression set**: designate 10–20 existing `e2e/scenarios/` tests as golden. The fine-tuned model must not regress any vs. the Mixtral baseline.
- **Fixed-prompt diff**: store ~50 reference prompts per engine where Mixtral produced known-good outputs. After fine-tuning: compute schema compliance and judge-pass rate; must match or beat baseline.
- **Latency floor**: fine-tuned 7B Q4 should be faster than Mixtral-8x7B. Track p50/p95 latency in the harness and alert on regression.
- **Fallback rate**: monitor `dialogue_degradation_level_total` metric. Ratio of `level="full"` should increase; ratio of `level="canned"` should be ≤1%.

### 4.5 Iterative Improvement Loop

```
Production (Ollama serving merged GGUF)
        │
        ▼
Hook wrapper logs (system, prompt, response, request_id) → JSONL
        │
        ▼
Offline filter (Section 2.3 quality gates)
        │
        ▼
Stratified sample for next training batch
        │
        ▼
Append to versioned dataset (dataset_v2.jsonl)
        │
        ▼
Train new LoRA adapter (Unsloth on local GPU)
        │
        ▼
Evaluate vs. held-out + golden regression set
        │
        ▼  (gate: match or beat current production adapter)
Merge to base → export GGUF → reload in Ollama
        │
        ▼
A/B test new adapter (per-engine config swap in llm_config.yaml)
        │
        ▼
Promote to default
```

Cadence: retrain every 5k–10k new high-quality examples per engine. Dialogue: possibly weekly. Memory consolidation: monthly.

## Section 5: Infrastructure Notes (Local GPU)

### 5.1 VRAM Requirements

QLoRA (4-bit base + LoRA adapters in bf16):

| Model | Min VRAM (training, seq=2048, batch=2) | Comfortable | Inference (Q4_K_M GGUF) |
|---|---|---|---|
| Mistral-7B-v0.3 (r=16, full modules) | 8 GB | 12 GB | 4.5 GB |
| LLaMA-3.1-8B (r=16) | 10 GB | 14 GB | 5.5 GB |
| Phi-3.5-mini 3.8B (r=8) | 5 GB | 8 GB | 2.5 GB |

An RTX 3090 (24GB) is comfortable for all configs. RTX 4070 (12GB) is tight for dialogue at seq=2048 with full modules — have batch=1 + grad_accum=16 ready as fallback. VRAM scales linearly with `max_seq_length` (KV cache during training is the dominant term for QLoRA).

### 5.2 Training Time Estimates

1000 examples × 3 epochs × effective batch 16 ≈ 190 optimizer steps:

| GPU | Mistral-7B QLoRA | Phi-3.5-mini |
|---|---|---|
| RTX 3090 (24GB) | 25–40 min | 10–15 min |
| RTX 4090 (24GB) | 12–20 min | 5–8 min |
| RTX 4070 (12GB) | 50–80 min | 20–30 min |

Memory consolidation at seq=2048 runs ~30% slower than dialogue. Quest slot-fill at seq=1024 runs ~2x faster.

### 5.3 Serving Fine-Tuned Models (Ollama Pipeline)

Ollama does not serve raw LoRA adapters — merge first.

1. **Train** → `adapter_model.safetensors` + `adapter_config.json`
2. **Merge** → `model.save_pretrained_merged("merged_dialogue_v1", tokenizer, save_method="merged_16bit")`
3. **Quantize** → `model.save_pretrained_gguf("merged_dialogue_v1", tokenizer, quantization_method="q4_k_m")`
4. **Create Ollama Modelfile**:
   ```
   FROM ./merged_dialogue_v1/unsloth.Q4_K_M.gguf
   TEMPLATE """{{ if .System }}<|im_start|>system
   {{ .System }}<|im_end|>
   {{ end }}<|im_start|>user
   {{ .Prompt }}<|im_end|>
   <|im_start|>assistant
   """
   PARAMETER stop "<|im_end|>"
   PARAMETER temperature 0.8
   PARAMETER top_p 0.95
   ```
5. **Register**: `ollama create npc-dialogue-v1 -f Modelfile`
6. **Configure**: update `engines/dialogue/llm_config.yaml` line 4 to `model: npc-dialogue-v1` — zero engine code changes required.

**Alternative**: vLLM with `--enable-lora` serves multiple LoRA adapters on a single base without merging. Switching from Ollama to vLLM is a one-class change in `engines/llm/` given the `LLMClientProtocol` abstraction.

### 5.4 Multi-Model Deployment

The architecture already supports per-engine LLM config (each engine has its own `llm_config.yaml` and injected adapter). Two options:

**Option A: Three separate Ollama models**
- Disk: 3 × ~4.5 GB ≈ 13.5 GB
- VRAM: ~3 × 5 GB = 15 GB concurrent; Ollama LRU-unloads idle models (configurable via `OLLAMA_KEEP_ALIVE`)
- Trade-off: 3–5s cold-start on first call to an unloaded model
- **Recommended starting point** — zero adapter code changes

**Option B: Single base + three LoRA adapters via vLLM**
- VRAM: 1 base (~5 GB Q4) + 3 adapters (~50 MB each) ≈ 5.2 GB total
- Per-request adapter selection via `lora_request` parameter
- Requires adding a vLLM adapter class to `engines/llm/` (one class, ~80 lines)
- **Best for VRAM-constrained deployment**

Dialogue serves user-facing traffic (60s timeout). Quest generation and memory consolidation run on the tick scheduler (offline). In practice, LRU eviction in Option A won't affect dialogue latency.
