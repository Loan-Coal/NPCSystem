## 2. New Findings

### [L1-08] `require_node` echoes user-supplied `node_type` in 404 message
Severity: MEDIUM · Confidence: Confirmed

`route_helpers.py:120`:
```python
raise HTTPException(status_code=404, detail=f"{node_type} not found")
```

`node_type` is taken directly from URL path parameters at `graph.py:53` and `graph.py:138`. A caller who requests `GET /v1/graph/nodes/<attacker-controlled>/foo` receives the exact string they sent back in the error body. This enables reflected XSS in HTML error renderers and can be used to probe internal type labels. `graph_error_to_http` was fixed (L1-02), but `require_node` was not updated alongside it.

Fix sketch: replace `f"{node_type} not found"` with the same constant `_NOT_FOUND_DETAIL = "Resource not found"` already used in `graph_error_to_http`.

### [L1-09] `delta_ticks` cap is enforced twice but inconsistently
Severity: LOW · Confidence: Confirmed

`clock.py:37` uses `Field(ge=1, le=MAX_DELTA_TICKS)` in the Pydantic model — this is the correct enforcement point. `clock.py:67-73` then re-checks `request.delta_ticks > settings.MAX_DELTA_TICKS` and raises HTTP 400. The second check is redundant and diverges if `MAX_DELTA_TICKS` is overridden in settings (the model is frozen to the module-level constant, while the runtime check reads settings). Not a security gap on its own but could allow the settings override to go unnoticed — the Pydantic check will always trigger first using the hardcoded constant.

Fix sketch: remove the redundant HTTP 400 check at clock.py:67-73 and rely solely on the Pydantic field validator.

### [L1-10] `IDEMPOTENCY_ENFORCE_HEADER=false` remains in shipped `.env` with only a warning, not a startup error, in staging/prod
Severity: MEDIUM · Confidence: Confirmed

`config.py:258-263` — when `IDEMPOTENCY_ENFORCE_HEADER` is `False` and `ENV != "dev"`, the engine logs a WARNING but starts successfully. All state-mutating endpoints (`POST /v1/clock/advance`, `POST /v1/action`, etc.) are therefore replay-able in staging/prod without any idempotency protection. This is the same issue as L1-06 but is PARTIAL rather than FIXED because the mitigation is advisory-only.

`.env:12`: `IDEMPOTENCY_ENFORCE_HEADER=false`

This is confirmed: the note in `config.py` explicitly says "warn (not error, for back-compat)". A licensing customer deploying to staging with a copy of this `.env` silently gets no idempotency protection.

Fix sketch: change the `if not self.IDEMPOTENCY_ENFORCE_HEADER and self.ENV != "dev"` branch to `raise ValueError(...)` instead of `logging.warning(...)`, or at minimum add a `.env.staging.example` that has it set to `true`.

### [L1-11] Schemes route (`GET /v1/npc/{npc_id}/schemes`) echoes caller-supplied `npc_id` in response body with no sanitization
Severity: LOW · Confidence: Confirmed

`schemes.py:41`: `"npc_id": npc_id` — the raw path parameter is included verbatim in the JSON response. This is not an injection risk in JSON context (the value is a string field), but it enables reflected content: a caller who sends a crafted npc_id like `"<script>..."` receives it back in the body. In practice only an issue if the response is rendered as HTML without escaping by a downstream consumer. Also enables topology enumeration confirmation (200 vs empty schemes list reveals whether an NPC id exists).

Fix sketch: validate `npc_id` against a whitelist pattern (e.g. `^[a-zA-Z0-9_-]{1,64}$`) at the route boundary before passing it to the reader; return the validated form.

### [L1-12] `.env` ships with `LOG_LEVEL=DEBUG` and `LOG_LLM_PROMPTS=true`
Severity: MEDIUM · Confidence: Confirmed

`.env:60-61`:
```
LOG_LEVEL=DEBUG
LOG_LLM_PROMPTS=true
```

The ENV-gate (`resolve_log_prompts`) correctly suppresses prompt logging in staging/prod. However `LOG_LEVEL=DEBUG` has no ENV gate — if this `.env` is used in staging/prod (common during initial deployment), all DEBUG-level messages from non-LLM modules (which may include graph node contents, player IDs, session tokens) are emitted to stdout/log aggregators. Combined with the advisory-only idempotency warning, this increases blast radius if logs are forwarded to external systems.

Fix sketch: add a `Settings` model validator that raises or at minimum warns when `LOG_LEVEL=DEBUG` and `ENV != "dev"`.

### [L1-13] `GET /v1/system/config` (runtime_config) and `/v1/system/metrics` are behind auth middleware but only require the base API key scope, not GRAPH_ADMIN
Severity: LOW · Confidence: Confirmed

`router_registry.py:79` — `system_v1_router` (which includes `/system/config`, `/system/engines`, `/system/metrics`, `/system/events`) is mounted under `API_V1_PREFIX` (not under `admin_prefix`). `middleware_helpers.py:78-85` — only paths starting with `admin_prefix` require `SCOPE_GRAPH_ADMIN`; all other authenticated paths get `required_scope=None` (auth validated, no scope check). Any holder of the base `API_KEY_SECRET` can read cadence config, engine status, and live event feeds — which may contain NPC ids and game world data. The `/system/events` endpoint returns full event dicts from the graph.

Fix sketch: move `system_v1_router` registration under `admin_prefix`, or add an explicit `SCOPE_GRAPH_WRITE` requirement for the event-feed and config endpoints.
