### [L9-01] `make demo-run` is RED live: the demo exhausts the WebSocket connection cap at ACT 6 of 12
Severity: **CRITICAL** · Confidence: **Confirmed**

**Evidence:** live run against the isolated stack (`NPC_BASE_URL=http://localhost:8001`), 1m52s:

```
[ACT 1] … >> Captain Sorn / Mira / Old Henryk    (3 WS turns, all fine)
[ACT 2] … >> Aldric                              (1 WS turn, fine)
[ACT 3] … >> Lira                                (1 WS turn, fine)
[ACT 6] … >> Mira (propagated rep): Traceback …
RuntimeError: WS dialogue error for mira_innkeeper: server rejected WebSocket connection: HTTP 403
EXIT_CODE=1
```

Server side, from the app container's log — exactly five accepts, then the cap:

```
INFO: 172.20.0.1:55638 - "WebSocket /v1/ws/dialogue" [accepted]
INFO: 172.20.0.1:46000 - "WebSocket /v1/ws/dialogue" [accepted]
INFO: 172.20.0.1:40346 - "WebSocket /v1/ws/dialogue" [accepted]
INFO: 172.20.0.1:43676 - "WebSocket /v1/ws/dialogue" [accepted]
INFO: 172.20.0.1:36904 - "WebSocket /v1/ws/dialogue" [accepted]
{"level":"WARNING","logger":"npc_engine.api.routes.dialogue.dialogue_ws",
 "message":"ws_connection_cap_reached","max":5}
INFO: 172.20.0.1:41012 - "WebSocket /v1/ws/dialogue" 403
```

`MAX_WS_CONNECTIONS_PER_KEY: int = 5` — `src/npc_engine/api/routes/dialogue/dialogue_ws.py:50`.

**Mechanism** (Confirmed for the leak, Likely for the precise cause). The client *does* close:
`demo_game/dialogue_ws.py:67` opens the socket in a `with websockets.sync.client.connect(...)`
block and `_recv_loop` returns on the `done` frame, so the context manager closes it. The five
sockets were opened over ~90 seconds and each had visibly finished before the next began — yet all
five slots were still held when the sixth connected. **The server is not releasing them.** After
`_run_first_turn`, the handler enters an idle-drain loop that only ever *sends*
(`dialogue_ws.py:231-233`: `while True: await drain_proactive_lines(...); await asyncio.sleep(0.5)`).
A Starlette WebSocket surfaces a client-initiated close as `WebSocketDisconnect` only on a
`receive()`; with an empty proactive queue the loop never receives and never sends, so
`except WebSocketDisconnect` (`:234`) never fires and `finally: await _release_ws_slot(key_id)`
(`:240-241`) never runs. The slot is held for the process lifetime.

**Already known:** no. Greps for `MAX_WS_CONNECTIONS_PER_KEY`, `ws_connection_cap`, "WS cap" and
"websocket" across `ISSUES.md`, `archive/ISSUES_RESOLVED.md`, `review-2026-08/TRIAGE.md` and
`review-2026-08/FINDINGS.md` return nothing but ISSUE-299 (a docs-drift issue about WS frame
types). This is new.

**Why it matters:** (a) the scripted hackathon demo — the studio-facing artifact — cannot be run to
completion on this tree; (b) the interactive demo is equally dead: `game_controller.py:179-270`
spawns a fresh `dialogue_ws_worker` thread, i.e. a fresh WS connection, **per dialogue send**, so a
human evaluator gets exactly **five lines of dialogue** before every further attempt 403s; (c) it is
a server-side resource leak, not merely a demo bug — every completed streaming conversation
permanently consumes one of five slots per API key, so a shipped deployment degrades to "no
streaming dialogue" after five conversations and only a restart recovers it; (d) it is
systemic-pattern #2 verbatim: 2026-06-03 L1-01 fixed "cap defined but never enforced" with a guard
test on `check_ws_connection_limit()` in isolation, and the *release* half of the same accounting
was never exercised end-to-end.

**Fix sketch:** make the idle loop disconnect-aware. Replace the sleep-only loop with an
`asyncio.wait_for(websocket.receive(), timeout=PROACTIVE_DRAIN_POLL_SECONDS)` inside the loop —
treat `TimeoutError` as "nothing from the client, keep draining" and a
`websocket.disconnect` message / `WebSocketDisconnect` as the exit — so a client close is observed
within one poll interval. Then add a test that opens `MAX_WS_CONNECTIONS_PER_KEY + 1` sockets
**sequentially**, closing each, and asserts the last one is accepted; the sequential case is the one
the current guard test does not cover. Gate it by putting a live `make demo-run` (not `--dry-run`)
behind a target the nightly can run (see L9-08).

### [L9-04] `keep_alive` prevents the *second* cold load, not the *first* — the demo's opening line costs 20 seconds
Severity: **HIGH** · Confidence: **Confirmed**

**Evidence:** Ollama held no resident model at stack boot (`/api/ps` → `{"models":[]}`). The first
dialogue turn: `load_duration_ms: 10515.194`, `duration_ms: 16733.745`, **HTTP end-to-end
20.098s**. Turns 2–4: `load_duration_ms` 7.863 / 10.272 / 10.065.
`llm_backend_load_latency_seconds` = `{count 4, sum 10.543394, min 0.007863, max 10.515195}` — one
load, three non-loads.

DEC-273 (`project-harness/DECISIONS.md:9539-9545`) says the 10.3s cold load was "**fixed** by
`keep_alive=30m`". Measured: `keep_alive` is sent and honoured (`/api/ps` showed a 29.5-minute
expiry), and it does eliminate *eviction* within a session. It cannot eliminate the load that
happens because nothing has asked for the model yet. Nothing in `main.py`'s lifespan warms the
model, so **every fresh boot, every machine restart, and every idle gap longer than 30 minutes puts
a 10.5s stall on the next player line** — 20.1s at the HTTP boundary, ~3× the 7s ceiling of the
stated budget.

**Already known:** partially — DEC-273 documents the 10.3s cold load and ISSUE-296..300 came out of
that work, but the "fixed" claim is the thing being contradicted here, and no issue tracks the
absent warm-up.

**Why it matters:** this is the *first* turn, which is the one a studio evaluator measures. It is
also the cheapest fix in this report.

**Fix sketch:** issue a zero-token warm-up on startup — a single `POST /api/generate` with
`{"model": …, "prompt": "", "keep_alive": <configured>}`. (Ollama returns `done_reason` immediately
for this shape; I used its mirror, `keep_alive: 0`, to unload at the end of this run, and it was
instant.) Fire it from `main.py`'s lifespan as a background task so boot is not blocked, and log an
`llm_warmup` record carrying the load duration so the cost stays visible. Guard it behind a setting
for the judge-model case (`e2e/helpers/judge_client.py` deliberately passes `5m`) so two models are
not pinned on a 12 GB card at once — DEC-229's graphics budget still applies.

### [L9-05] `llm_tokens_in_total` excludes the system channel and under-counts real input tokens by 4.3×
Severity: **MEDIUM** · Confidence: **Confirmed**

**Evidence:** after four turns, `llm_tokens_in_total = 6,541`. Ollama's own `prompt_eval_count` for
the same four calls: 6,902 + 7,019 + 7,165 + 7,326 = **28,412**. The counter is
`estimate_tokens(prompt)` — `src/npc_engine/engines/dialogue/llm_client.py:96` and `:229` — and
`prompt_chars` alone sums to 5,749 + 6,180 + 6,798 + 7,442 = 26,169 chars, which at `len // 4` is
**6,542**. The counter matches the user prompt exactly and therefore excludes `system_chars: 22829`
per call entirely. (`llm_tokens_out_total` = 714 against an `eval_count` sum of 582 — also an
estimate, 1.23× high in the other direction.)

**Why it matters:** the system prompt is **78% of what the model actually reads** and it is
invisible to the only in-process input-token counter. Any budgeting, cost model, or "can a smaller
model fit this?" reasoning taken off `llm_tokens_in_total` is off by more than 4×.
`prompt_eval_log.py`'s own docstring says character counts are logged raw precisely so the
`len // 4` estimate can be checked against reality — this is that check, failing. It also
understates the size of the prize: ~5,700 tokens of fixed system text per turn is the biggest lever
available to the small-model goal, and nothing counts it.

**Fix sketch:** either add the system channel to the estimate at both call sites, or — better —
stop estimating and increment `llm_tokens_in_total` / `llm_tokens_out_total` from the backend's own
`prompt_eval_count` / `eval_count`, which the adapter already parses for `prompt_eval_log`. Keep the
estimate as a *separate* metric if the drift is itself worth watching, but do not let the estimate
be the headline number. Pin it with a test that asserts the counter and the reply's
`prompt_eval_count` agree within a tolerance on a recorded reply fixture.

### [L9-06] The shipped latency instrumentation cannot express the latency budget it exists to defend
Severity: **MEDIUM** · Confidence: **Confirmed**

**Evidence:** `GET /v1/admin/system/metrics` returns, for `llm_backend_latency_seconds`, only
`{"count","sum","min","max"}` — no buckets. This is deliberate and documented at
`src/npc_engine/engines/llm/llm_metrics.py:12-14`. The dialogue budget DEC-273 defends is "3–7s",
which is a **tail** property; the only tail statistic available is `max`, which is dominated by the
single cold outlier (16.73s here) and says nothing about the 95th percentile of warm turns. My own
p50/p95 for this run had to be derived by hand from four `llm_prompt_eval` log lines, which does
not scale and is not queryable.

**Why it matters:** this is the asserted-not-measured pattern one level up — DEC-273 built
instrumentation, and the instrumentation cannot answer the question DEC-273 exists to answer.
Anyone reading `sum/count` off this endpoint as a p50 (the docstring explicitly forbids it, which
means someone eventually will) gets 8.11s for a run whose warm p50 was ~4.9s.

**Fix sketch:** either add a small fixed-bucket histogram alongside the summary for
`llm_backend_latency_seconds` (buckets at 1 / 2 / 3 / 4 / 5 / 6 / 7 / 10 / 15 / +Inf seconds map
directly onto the 3–7s budget), or have the eval harness aggregate percentiles from the
`llm_prompt_eval` records it already emits and record them next to the existing
`latency_p50_ms` / `p95` it produces. The second is cheaper and reuses a channel that exists.

### [L9-07] `check-rules` reports a resolved baseline entry on every run and never ratchets it down
Severity: **LOW** · Confidence: **Confirmed**

**Evidence:** `make check` prints, immediately above its own OK line:
`check-rules: 1 baselined violation(s) resolved - run the update target to ratchet down.`
then `check-rules: OK - no new violations (115 grandfathered).` The gate passes either way, so the
message has no consequence and the freed slot stays in `scripts/rules_baseline.txt`.

**Why it matters:** a grandfathered slot that has been vacated is a slot a future violation can
silently re-occupy without the gate reddening. It is small, and it is exactly the failure mode the
ratchet exists to prevent.

**Fix sketch:** run `make check-rules-update` and commit the tightened baseline (115 → 114).
Longer term, decide whether a resolved-but-unratcheted entry should be a *failure* rather than a
notice — that is a DECISIONS call, since it makes the gate stricter than DEC-226 currently requires.

## Notes and caveats on my own measurements

- **All latency numbers were taken with `LOG_LEVEL=DEBUG` and `LOG_LLM_PROMPTS=true`**, which is
  what the untracked local `.env:60-61` ships (`.env.example:75-76` correctly ships `INFO` /
  `false`). This makes the app serialise the entire ~22.8k-char system prompt into a DEBUG record
  before every call (`llm_client.py:97-99`, correctly gated by `self._log_prompts`). The cost sits
  outside the backend-latency window and is small — `duration_ms − total_duration_ms` was 39–55ms
  across all four turns — but the end-to-end HTTP figures (5.26–6.39s warm) include ~0.4s of engine
  overhead a production config would partly avoid. The backend numbers are the ones to quote.
- **No judged eval score is cited anywhere in this document.** Everything here is a command exit
  code, a wall clock, a metrics counter, a backend-reported duration, or a graph edge.
- Four dialogue turns is a small sample. It is enough to answer the `keep_alive` question
  definitively (a ~1,000× drop in `load_duration_ms` is not noise) and enough to show the DEC-273
  warm constants do not reproduce, but the warm p50/p95 should be re-measured over ~30 turns before
  anyone writes a number into a decision.
- The integration suite was deliberately not run (ISSUE-277); no measurement here depends on it.
  ISSUE-278's flake was not encountered because no integration test executed.
