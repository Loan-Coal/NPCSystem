  `gen_digest_fn = fetch_generation_digest or _engine_adapter.fetch_model_digest` /
  `judge_digest_fn = ... or _engine_adapter.fetch_model_digest` /
  `version_fn = fetch_ollama_version_fn or _engine_adapter.fetch_ollama_version` — the
  live-network fallback TRIAGE.md quoted verbatim, present at HEAD of this branch.

Neither CR-L01-01 nor CR-L15-01 is named, greppable, or logged anywhere in `ROADMAP.md`
(`grep -n "GraphUnavailableError\|503\|distorted_summary\|fetch_ollama_version\|model_digest"
project-harness/ROADMAP.md` → 0 relevant hits). They are not in Sprint 9's eval-repair sketch,

that came before it" (line 4), but two data-integrity defects survive under a different id
namespace (`CR-L*` vs `L*`) that the 2026-09-07 review never cross-referenced, so the T

propagation mechanism that discards distortion on read makes that revival partly pointless).
CR-L15-01 undermines the eval-comparability guarantee the owner explicitly chose to
"keep and repair" (Sprint 9) and that DEC-281/T16.4 is trying to harden with `engine_build_sha`
— a run with a null generation digest is exactly the kind of unattributable row T16.4 exists to
prevent, from a different code path the T programme never looked at.
**Proposed fix:** add two tasks (or fold into existing sprints): (a) a Sprint-3/gossip task
fixing the propagate-read query to select `k.distorted_summary` with `best_event.summary` as
fallback only when no `KNOWS_ABOUT` edge exists yet, with a RED anchor asserting a two-hop
propagation actually shows drift; (b) a Sprint-9 prerequisite task injecting fakes for
`fetch_ollama_version_fn`/`fetch_generation_digest`/`fetch_judge_digest` in the 15 uninjected
call sites `run_config.py` and its tests exercise, so CI stops silently recording `None`
digests before T18.2's re-baseline runs on top of it. Also add a one-line note at the top of
`ROADMAP.md`'s History table: "`review-2026-08/TRIAGE.md`'s CRITICALs were re-triaged for this
programme; N are fixed, M are still open and tracked as ISSUE-34x."

### [R6-03] ISSUE-339 (probe engine-name mismatch) is untouched by T15.1 despite owning the same subsystem
Severity: MEDIUM · Confidence: Confirmed
**Affects:** T15.1
**Evidence:** `ISSUES.md:115-133`, ISSUE-339: 10 of 11 `evals/probe_*.py` modules pass an
`engine_name` to `probe_runner.py:204`'s `_merge_status_metrics` that the scheduler never
registers (`"events"` vs `"event"`, `"memory"` vs `"memory_consolidation"`/`"memory_decay"`,
etc.), so those probes silently get no `tick_count`/`error_count`/`duration_ms`. T15.1's
`Files:` line is `scheduler/engine_status_store.py`, `scheduler/tick_scheduler.py`,
`api/routes/admin/system.py`, two new test files — no `evals/probe_runner.py`, no
`evals/probe_*.py`. T15.1 is not in ISSUE-339's text and ISSUE-339 is not in T15.1's Findings
line.
**Why it breaks the programme:** T15.1's stated point is closing "the observability gap that
let every finding in this programme hide" (Sprint 8 header) by adding `working_set_size` to
`EngineStatusRecord`. That new field will be exactly as invisible to the 10 mis-mapped probes
as `last_error`/`error_count` are today, for the identical reason. Sprint 8 will ship believing
it fixed observability while the eval-side consumer of that observability stays broken.
**Proposed fix:** either fold ISSUE-339's fix into T15.1 (map each probe's `engine_name` to a
real scheduler key, or have `_merge_status_metrics` warn on a miss) or add a one-line
cross-reference in T15.1's Spec: "does not fix ISSUE-339 (probe name mismatch) — that must land
separately before probes can observe `working_set_size`."
