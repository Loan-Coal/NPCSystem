### [R5-01] "1-2 sessions for all six" (Parked, ROADMAP.md:1413-1416) is optimistic by roughly an
order of magnitude for the smallest engine alone
Severity: HIGH · Confidence: Confirmed
**Affects:** Parked section ("Rebuilding the political layer"), T1.2, T3.1, T3.2, T4.2, T6.2, T9.1,
T10.1, T10.2, T12.1

**Evidence:** I read `src/npc_engine/engines/treaty/treaty_engine.py` (84 lines) end to end — the
smallest and simplest of the six deleted engines (no LLM, one injected port, two methods). `git show`
gets the engine file and its port/repo back verbatim for free; that is not what "restore" costs.
Tracing what T3.2 actually removes around it (`ROADMAP.md:477-497`) and what Sprints 4-8 add
*after* it is gone:

1. **Port + repository are deleted, not just the engine.** T3.2 deletes `treaty_port.py` and
   `treaty_repository.py` alongside the engine (`ROADMAP.md:479-482`). `git show` recovers the text,
   but `TreatyGraphPort` will not exist post-Sprint-5 as a *pattern* to restore into — T9.1 has
   collapsed the remaining ports to concrete injection (`ROADMAP.md:824-838`), so the correct
   restoration is a concrete `Neo4jTreatyRepository` injected directly, which is a **design decision
   about what the code should look like now**, not a paste.
2. **The wiring is deleted, not stubbed.** `tick_scheduler.py`'s `treaty_engine` constructor
   parameter and its `_ordered_tick_engines()` entry are explicitly removed by the T3.1/T3.2 checklist
   item 6 (`ROADMAP.md:467`, reused by T3.2). Confirmed live today: `tick_scheduler.py` currently
   carries `treaty_engine: TickEngine | None = None` at the constructor and `("treaty", self._treaty_engine)`
   in the ordered list — both gone after T3.2, both must be hand-rewritten, not copied.
3. **`api/dependencies_advanced/politics.py` is deleted wholesale**, not edited — its own docstring
   (currently: "Singleton factory providers for political/faction engines — treaty, oath, succession,
   agenda, military") says its only reason to exist is these five engines. Restoring one engine means
   recreating this file (or a successor) from scratch, including its `lru_cache` factory and
   `dependencies_infra` wiring, since nothing else in the tree will import it once all five callers
   are gone.
4. **T6.2 pins the tick order as a literal expected sequence, not derived from source**
   (`ROADMAP.md:652-658`: "keep the expected list literal in the test, never imported from the source
   it checks, or it asserts nothing"). Re-inserting a restored engine requires editing that hardcoded
   list and reasoning about its correct position from L13.md's read-after-write pairs — pairs that, by
   definition, will not mention an engine that was deleted before T6.2 ran. This is domain judgement,
   not a git-show.
5. **The gates built in Sprints 5-6 actively resist the restore.** `check_dip_threshold.py` (T10.1)
   will fail on a re-added single-implementor port unless a `scripts/dip_waivers.txt` line with a
   `DEC-NNN` is added (`ROADMAP.md:901-903`); `check_loc_ratchet.py` (T10.2) fails on any net-positive
   `src/npc_engine` LOC unless `scripts/loc_baseline.txt` is deliberately bumped with a stated reason
   (`ROADMAP.md:927-929`); `check_dead_surface.py` will have already flagged and let T10.2 delete
   `TREATY_LLM_EVAL_ENABLED` from `config.py` once its only reader (the engine) is gone — so restoring
   the engine also means restoring a `Settings` field and its own test. `check_test_quality_can_fail.py`
   (T12.1) must pass on whatever tests come back. None of this is exotic, but every one of these is a
   gate this programme built *specifically* to make re-adding deleted code cost something.
6. **`make check` is ~11m58s per iteration** (measured fact table, `REVIEW_SPEC.md:50`) and the loop
   gates one task to one commit; a restoration touching 6+ files across `engines/`, `graph/`,
   `scheduler/`, `api/`, `docs/`, plus new/updated tests, plus at least 2-3 gate-failure iterations,
   realistically costs several `make check` cycles by itself — 35-55 minutes of gate time alone,
   before writing any code.

**Total, for `treaty` alone** (the cheapest of the six by LOC: 84+39+59 = 182 lines pre-deletion):
recreate 3 files (trivial) + rewire 4 call sites (30-60 min, needs correct tick-order reasoning) +
recreate the factory module (20-30 min) + restore the `Settings` field + its test (15-20 min) +
satisfy DIP/dead-surface/LOC-ratchet/test-quality gates including at least one `DECISIONS.md` entry
for the baseline bump (30-45 min) + `docs/ENGINES.md` row (5 min) + 2-3 `make check` cycles
(35-55 min) = **roughly 3-4.5 hours of single-session work for the single simplest engine**, not the
~15-30 minutes "1-2 sessions for all six" implies (90-180 min / 6 ≈ 15-30 min each). `agenda` (354
LOC across 3 files, `conversation_intent_service.py` + `intent_formation_engine.py` besides the
engine itself) and `military` (below, R5-03) cost substantially more than `treaty`.

**Why it breaks the programme:** this is a "Parked" note, not a gated task, so it does not fail
`make check` — but section 0 requires flagging anywhere a locked decision's consequences are
mis-stated, and the task text says explicitly "the owner's decision rested partly on it." If a studio
prospect asks for political/military mechanics in month 4, the owner will plan around a 1-2 session
estimate that is off by 5-10x for the cheapest engine and worse for the others, and will discover the
gap only when already committed to the timeline.

**Proposed fix:** change the Parked entry to: "recoverable in **source**, but restoration into the
post-Sprint-5/6 codebase (concrete injection, DIP/LOC-ratchet/dead-surface gates, pinned tick order)
is a redesign exercise per engine, not a paste — budget 1 engine per session at minimum, more for
`agenda` and `military` (see R5-03 for `military`'s added cost)." Do this before any studio
conversation cites the current estimate.

Severity: HIGH · Confidence: Confirmed
**Affects:** T1.2, T13.1, T13.2 (Sprint 7 census/trim never reaches this)

**Evidence:** `docs/DEMO_SCRIPT.md:37,63-71,180-184` scripts Act 5 as "Military engine. Iron Legion,
strength 100, faces City Guard, strength 60, at the barracks. One clock tick" and narrates
"WORLD feed: battle resolved. Iron Legion wins." Its own sign-off checklist
(`docs/DEMO_SCRIPT.md:255`) requires "WORLD feed: at least one `battle` event visible after military

`NarratorCue("pre_military_cue", ...)` → `ClockTick(name="military_tick", ...)` →
`NarratorCue("pre_world_feed_cue", text="[NARRATION] WORLD feed -- battle event surfaced by the
military engine.")` → `WorldFeed(name="world_feed_battle", limit=8)`.
T1.2 deletes `military_engine.py`, the only writer of the `CONTROLS`/battle event
(`ROADMAP.md:341-369`), specifically because it ends the game on tick 5. After T1.2, the clock tick
in Act 5 still fires but nothing writes a battle event — the feed step returns whatever is already in
the last-8 window, not a battle. Neither `docs/DEMO_SCRIPT.md` nor `demo_game/runners/run.py` is in
T1.2's `Files:` list, T13.1's census ("record which modules are actually imported and executed"), or
T13.2's deletion pass — the census would in fact mark the `WorldFeed`/military beat "executed" (it
still runs, it just produces nothing) and keep it, since the census tests reachability, not
correctness of the narration.

**Why it breaks the programme:** the roadmap's own priority-1 goal is "It works. A studio evaluator
can boot the stack, play the demo end to end, and see NPCs remember, feel, and gossip"
(`ROADMAP.md:9`). T1.2 is executed in Sprint 1, before any live verification of the demo beyond
T1.1's fix — nobody re-runs the scripted demo end-to-end against `docs/DEMO_SCRIPT.md` after T1.2
specifically. This is the one Act of the studio-facing narration script that stops matching the
product it is meant to sell, and it is the very sprint whose stated goal is "the demo works again."

**Proposed fix:** add a line item to T1.2 or T13.2 (whichever the owner prefers): "Rewrite
`docs/DEMO_SCRIPT.md` Act 5 and `demo_game/runners/run.py`'s ACT 5 block to replace the military beat
with a beat the surviving engines can actually produce (e.g. an existing gossip/quest/emotion payoff),
or delete Act 5 and renumber. Do not leave a beat in the studio-facing script that narrates a system
that was deleted for causing the demo's worst bug."

### [R5-03] The `military` deletion is the one most likely to be regretted, and it is not a
restoration — it is unsolved feature work
Severity: MEDIUM · Confidence: Likely
**Affects:** T1.2, Parked ("Rebuilding the political layer")

**Evidence:** `military` is deleted first and alone (T1.2, Sprint 1) specifically because it is
unconditionally gated — `tick_scheduler.py:356` runs it in the plain every-tick list with no cadence
gate, and `military_engine.py:49` calls `resolve_battles(...)` unconditionally every tick
(`ROADMAP.md:341-369`). Restoring the engine from git, as the Parked note implies, restores exactly
that defect — armies co-located in the seed will resolve a battle on the very next tick, again
ending the game the way it did before T1.2. A correct restoration is not "put the file back"; it is
"design and implement a cadence gate, a trigger condition, or a seed change that keeps armies apart
until the player is meant to see a battle" — genuinely new design work, not recovery. Of the six
engines, `military` is also the one demo pitch decks are most likely to reach for (armies, territory,
war — the pitch line in `docs/DEMO_SCRIPT.md:137-138`, "The global NPC AI market hits $2 billion...
No one has cracked persistent knowledge propagation," does not mention strategy/war, but any studio
with a 4X or grand-strategy angle will ask for exactly this).

**Why it breaks the programme:** not an execution defect — a product-positioning one. The programme
correctly prioritises the demo that exists today (gossip, memory, dialogue) over political/military
mechanics nobody is currently selling. But it deletes the single most "campaign-shaped" system in the
portfolio and files its return under "recoverable," when in fact recovering it safely requires solving
the design problem that got it deleted in the first place.

**Proposed fix:** none required for the locked decision (do not relitigate the deletion). Amend the
Parked note for `military` specifically to say restoration requires a cadence/trigger design, not
just code recovery, distinguishing it from the other five (which are closer to a genuine
"put it back" cost, albeit still underestimated per R5-01).

### [R5-04] `scripts/dip_waivers.txt` has an unenforced justification field — a fill-forever valve,
not a threshold
Severity: MEDIUM · Confidence: Likely
**Affects:** T10.1

**Evidence:** `ROADMAP.md:901-903`: "Provide a documented waiver file, `scripts/dip_waivers.txt`, for
protocols kept deliberately, each line requiring a `DEC-NNN` reference. An empty waiver file is the
target state and the gate should report how many waivers are in use so the number is visible." The
spec requires a `DEC-NNN` reference to *exist* on each line; nothing in the spec requires the gate to
validate that the referenced decision actually argues the protocol deserves 2+ implementors/3+
callers, or that the decision hasn't been superseded. A `DEC-NNN` reference is a citation, not an
argument — the gate can only check its presence, not its truth.

**Why it breaks the programme:** rule 4 exists because 34 of 44 protocols failed the 2+/3+ threshold
at review time (`ROADMAP.md:828-829`) — the review's single largest structural finding. A waiver file
whose only enforced property is "cites a decision number" reproduces the same failure mode one layer
up: instead of unjustified protocols, the codebase accumulates unjustified *waivers*, each individually
legitimate-looking (it cites something) and collectively defeating the rule. The count being "visible"
is transparency, not a limit — nothing stops it growing indefinitely, and nothing in the 9 rules or
their gates revisits an existing waiver later.

**Proposed fix:** cap the waiver file at a small fixed size (e.g. the 9 protocols T9.1 explicitly
names as keepers) enforced by the gate itself, and require a second, periodic gate (or a documented
manual review cadence in `ROADMAP.md`/`ISSUES.md`) that re-justifies every waiver against current
implementor/caller counts rather than trusting the original citation forever.

### [R5-05] The reverse LOC ratchet's only stated remedy for a legitimate feature is "bump the
baseline with a reason" — no gate checks the reason, and adjacent directories are uncounted
Severity: MEDIUM · Confidence: Likely
**Affects:** T10.2, T12.1, T15.1, T16.2, T16.3

**Evidence:** `ROADMAP.md:927-929`: "**LOC ratchet** (`check_loc_ratchet.py`): count non-test LOC
under `src/npc_engine/` and compare to `scripts/loc_baseline.txt`. Fail if it rose. Raising the
baseline is a deliberate edit with a reason in the commit message." The gate checks a number against
a file; the "reason" lives only in prose in a commit message that no script re-reads or validates.
Sprints 6-8 already add code after the ratchet lands in T10.2 (T12.1's gate script, T15.1's
`working_set` field, T16.2's histogram buckets, T16.3's `case_set_version` split — T16.3 itself notes
"LOC delta is positive (about +15)... state in the completion note that this buys the comparability"),
so the baseline is bumped repeatedly within this same programme, by design, within weeks of being
seeded. The ratchet counts `src/npc_engine/` only — `tests/`, `scripts/`, `evals/`, `demo_game/` are
uncounted, and this review's own spec names that exact loophole for R4 (R4.2); from the product/rot
angle the same fact means a future contributor under time pressure has an easy, gate-invisible way to
ship a feature ("move the logic to a script the tick calls" or "put the real implementation under
`evals/` and import it back") that the gate cannot see even in principle.

**Why it breaks the programme:** a ratchet that is bumped on a predictable cadence within the same
programme that installed it, with no automated check on the stated reason, teaches contributors that
"reverse LOC ratchet" means "ask for an exception," not "the number only goes down." Rule 9's own
sibling rule (net-negative phases) has the identical shape: it is a reporting obligation with no gate
enforcing the report is truthful.

**Proposed fix:** none of this argues against the ratchet (locked decision, rule 1) — but
`ROADMAP.md` should say explicitly, next to rule 1 and rule 9, that a baseline bump requires a
one-line justification *reviewed by a human*, not just present in a commit message, and should note
the uncounted-directory loophole as a known limitation rather than silence, so a future maintainer
does not mistake "LOC dropped in `src/`" for "the codebase got smaller."

### [R5-07] The deferred-backlog audit (T0B.2) is non-blocking by design, and this repo has already
lived through exactly this decay once
Severity: HIGH · Confidence: Confirmed
**Affects:** T0B.2, T6.3, T13.1, T13.2, T15.2, T16.1, Sprint 9, Sprint 10

**Evidence:** `ROADMAP.md:265`: "Do not make it fail the night — it is a report, not a gate." The
five flagged in-fence tasks (T6.3, T13.1, T13.2, T15.2, T16.1) and the entirety of Sprints 9-10 are
structurally exempt from the loop (`compute_next` never returns a flagged task,
`ROADMAP.md:280-282`), and their only enforcement is a printed report at the start and end of a loop
run that exits non-zero but blocks nothing. This repo has direct, first-party precedent for exactly
this failure: T0's own Provenance note (`ROADMAP.md:149-152`) states "R6 was archived on 2026-09-08 as
part of clearing the roadmap while all three of its tasks were still unticked — that was an error, and
this sprint corrects it." Deferred, unattended-unsafe work sat archived-and-forgotten until a *second*
review cycle rediscovered it and had to reinstate it as Sprint 0. The mechanism that let that happen
(a roadmap rewrite silently dropping unticked flagged work) is not fixed by T0B.2 — T0B.2 only makes
the current backlog *visible*, it does not stop a future roadmap replacement from doing the same thing
again to Sprints 9-10 if the T programme is itself later "retired and archived" the way the M
programme was (`ROADMAP.md:3`).

**Why it breaks the programme:** the programme's two most important untested claims — that `routine`
and `need_decay` actually move NPCs (T6.3) and that the surviving engine portfolio actually does work
(T15.2) — are exactly the flagged, easy-to-skip work. If nobody runs the interactive sessions, the
roadmap reads "Sprint 8 complete" while its central claims (the world is alive, the census gap is
closed) are unverified, which is precisely the shape of defect this whole programme exists to prevent
("a gate that green-lights a broken product is worse than no gate," `ROADMAP.md:29`) — except here it
is not a gate lying, it is the *absence* of one, which the roadmap itself says is acceptable
("skipping costs nothing where attempting costs a whole session," `ROADMAP.md:280-281`) without also
saying what makes the human follow-through happen.

**Proposed fix:** name an owner and a deadline for each of the five flagged tasks and Sprints 9-10 in
`ROADMAP.md` itself, next to the Deferred backlog table, not just a machine-audited list — a report
nobody is assigned to read is the same as no report, and this program has already proven that once.

### [R5-08] Rule 7 ("one path per concept") has no gate, and this very programme creates a new
instance of the pattern it names — read-only services over data nothing writes any more
Severity: MEDIUM · Confidence: Confirmed
**Affects:** T3.2, T4.1, rule 7

**Evidence:** T3.2 itself says, in its own text (`ROADMAP.md:488-490`): "Behavioural consequence to
state plainly in the completion note: standings no longer decay and treaties no longer expire, so
that data becomes static. The owner accepted this on 2026-09-08... it must be written down rather than
discovered later." This is the *converse* of the "engine + parallel graph service" duplication rule 7
was written to catch — here there will be exactly one path (the service), but it silently stops being
a live path and becomes a frozen snapshot, which is arguably just as misleading to a future
maintainer reading `FactionService`/`pledge_service`/`treaty_service` and assuming standings evolve.
None of the 9 rules or their gates (`check_engine_census.py`, `check_dead_surface.py`,
`check_dip_threshold.py`) would catch "this service's backing data is frozen" — the only defence is
the completion-note prose T3.2 asks for, which is process, not a mechanism.

**Why it breaks the programme:** the roadmap is aware of this specific instance and handles it by
convention (write it down). But the underlying gap — nothing detects "a read path survives its last
writer" — is general, and the next time an engine is deleted for being dead weight while a route or
service keeps reading its old data (which is exactly what `demo_game` and eval cases already do for
several deleted engines per R2's scope), the same silent staleness recurs with no rule catching it,
only whoever remembers to write the DECISIONS.md note this time.

**Proposed fix:** extend `check_engine_census.py` or `check_dead_surface.py` with one more check: any
graph service/repository under `graph/` with **zero** remaining engine or route writer (only readers)
gets flagged as "frozen data" rather than silently passing rule 3's "has a live caller" test — a
reader is a caller, but a service with readers and no writers is exactly the shape T3.2 already
diagnosed by hand.

Severity: HIGH · Confidence: Confirmed

**Evidence:** `ROADMAP.md:1358-1380`: Sprint 9 is explicitly "Sketch, to be detailed into tasks when

position as today, just with more infrastructure underneath it.

happen automatically" note directly under the Sprint 9 header, and add it to the deferred-backlog
table T0B.2 builds, not only Sprints 1-8's five flagged tasks — Sprint 9/10 are a bigger, longer-lived
version of the same risk.

### [R5-10] Rule 8 ("prefer deterministic over model") has zero enforcement surface among the 9
rules' gates
Severity: LOW · Confidence: Confirmed
**Affects:** rule 8 (ROADMAP.md:66-67)

**Evidence:** Rules 1, 3, 4, 5, 6 each name a gate in the roadmap's own preamble
(`check-loc-ratchet`, T10.2's dead-surface/rule-3 gate, `check_dip_threshold.py`,
`check_test_quality_can_fail.py`). Rule 8 ("A model call is a budget item, not a default.
`engines/gossip/` is the in-repo precedent") names no gate anywhere in the 39 tasks. The "Parked" note
on deleting the quest slot-fill LLM call (`ROADMAP.md:1417-1419`) is explicitly rule-8-motivated but
is itself unscheduled, blocked on Sprint 9.

**Why it breaks the programme:** of the 9 rules, this is the one most directly tied to "the
small-model goal" this repo's other tooling (the `/full-review` skill, per the review spec's
framing) is weighted toward, and it is the one rule that survives purely as prose. A future feature
that defaults to an LLM call where a deterministic path would do will not fail any check this
programme installs.

**Proposed fix:** even a soft signal — a script that greps new/changed engine code for
`llm_client\.|generate(_structured)?\(` calls without an adjacent deterministic fallback path, and
reports rather than fails — would give rule 8 the same visibility rule 3's dead-surface report gives
rule 6, without needing a hard gate.
