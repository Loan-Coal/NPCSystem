## Claim verdicts

**1. "`oath` and `treaty` are known-shape duplicates (both expiry + violation)."** —
**CONFIRMED.** Read `src/npc_engine/engines/oath/oath_engine.py:1-58` against
`src/npc_engine/engines/treaty/treaty_engine.py:1-52`: both classes take exactly one injected
`*GraphPort`, both `run_tick` bodies are (1) fetch-expiring → expire/break, (2) count
violations among what remains, (3) return a two-key result dict (`expired_*`/`violated_*` or
`violations_detected`). The module docstrings are templated near-verbatim ("Graph access is
injected as a `X`GraphPort (DEC-122 / SEV-24); the engine holds no Neo4j session."). Both are
also identically unreachable from the API (routes use `pledge_service`/`treaty_service`
instead — see [L10-03]). This is close to a mechanical extract-a-base-class opportunity.

**2. "`agenda`, `succession` and `faction_politics` are all political tallies — three engines
doing one job."** — **PARTIALLY CONFIRMED, overstated as "one job".** `agenda_engine.py:1-10`
and `succession_engine.py:1-10` do share infrastructure — same `PoliticalGraphPort`, same
"Phase 7.2 Political Simulation" docstring template — but their logic differs: agenda tallies
`SUPPORTS_AGENDA`/`OPPOSES_AGENDA` weights and marks pass/fail (a genuine tally), while
succession detects vacant titles and *grants* them to the first eligible heir (an
assignment, not a tally). `faction_politics_engine.py:1-9` is architecturally separate — a
different port (`FactionPoliticsGraphPort`) and a different rules loader
(`FactionPoliticsRules`), doing event-driven standing decay toward neutral, not tallying
anything. Verdict: agenda+succession share a real duplicate-infrastructure risk (2, not 3);
faction_politics does not belong in that group.

**3. "`military` is a documented no-op stub."** — **REFUTED. The docstring is wrong; the
engine is real.** `military_engine.py:34-64` calls `resolve_battles()` (219-line
`military_battle_service.py`: strength comparison, damage, `CONTROLS`/`OCCUPIES` updates, a
battle `Event` node) and `process_resource_yield()` (113-line
`military_resource_service.py`) on every tick, returning
`{"battles_resolved": N, "factions_yielded": M}`. `tick_scheduler.py:131-132` still says:
*"military_engine: ... currently a no-op stub (see ISSUES.md ISSUE-001)"* — this is doubly
wrong: (a) it hasn't been a stub since milestone S6.5 (confirmed by
`archive/ISSUES_RESOLVED.md:1372-1383`, `[FIXED] ISSUE-111`, closed 2026-06-19 — over two
months of tree history ago), and (b) `ISSUES.md` `ISSUE-001` is an unrelated, also-resolved
issue about `top_p`/`stop_sequences` forwarding, not military at all. See [L10-04].
Already known: `CR-L14-01` (HIGH, Confirmed) and `CR-L09-06` (MEDIUM, Confirmed) already flag
that `military_engine.py:34`'s signature dropped a `session` kwarg the tests/docstrings still
assume — same underlying "docs/tests describe a military engine that no longer exists"
pattern this finding extends to the tick_scheduler docstring specifically.

### [L10-01] `currency` is a fully vaporware engine with its own contract and contract test
Severity: MEDIUM · Confidence: Confirmed
**Evidence:** `src/npc_engine/engines/currency/__init__.py` (12 lines, docstring only — "Public surface: (list re-exports here)"); `src/npc_engine/engines/contracts/currency_engine.yaml` declares a contract for it; `tests/contract/test_currency_contract.py` exists and presumably validates that YAML in isolation (schema-only, since `contract_loader.py:8` states "Does NOT: enforce contracts at runtime").

**Fix sketch:** Either implement the currency engine the contract promises, or delete `engines/currency/`, `engines/contracts/currency_engine.yaml`, and `tests/contract/test_currency_contract.py` together, and confirm `CURRENCY_MAX_PER_TRANSACTION`/`CURRENCY_MAX_PER_SESSION` are genuinely enforced elsewhere before deleting the contract's safety claim.

### [L10-03] Five of seven "political" tick engines are invisible to the API — routes read the same domain through a separate, hand-written graph-service layer instead
Severity: MEDIUM · Confidence: Confirmed
**Evidence:** `oath` (`pledges.py` uses `graph.political.pledge_service`), `treaty` (`treaties.py` uses `graph.political.treaty_service`), `faction_politics` (`factions.py` uses `graph.faction.faction_service`), `player_model` (`player_model.py` uses `graph.character.player_model_writer`), and `reputation` (`reputation.py` uses `graph.reputation.reputation_service`) all have a dedicated Engine class wired into `TickScheduler`, and a same-named API route — but the route imports a parallel graph-layer service, never the Engine class itself. `succession`, `skill`, `mood`, `clique`, `routine` don't even have that fallback route.
**Why it matters:** This is a structural pattern, not five coincidences: every "political"/social tick engine ships alongside a duplicate read/write surface in `graph/`. Either the Engine classes are the wrong abstraction (the graph-service layer does the real work and the Engine classes are a redundant tick-only wrapper around the same Cypher), or the API layer should be calling the engines and currently doesn't (functional drift risk — two code paths that must independently stay correct). Either reading argues for consolidation before the small-model goal has to pay for both.
**Fix sketch:** Pick one per engine: (a) fold the tick-only Engine class's logic into the graph service and have `TickScheduler` call the service directly, removing the Engine class, or (b) route API endpoints through the Engine class and delete the parallel graph-service methods. Do not leave both live indefinitely — that's the ISSUE-165-style "two paths, one intent" trap the ledger already tracks elsewhere.
