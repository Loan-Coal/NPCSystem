## Findings

### [L6-01] Iron Legion auto-conquers Guard Barracks on the first clock tick — "win" is unreachable, "lose" is the default outcome
Severity: **CRITICAL** · Confidence: **Confirmed** (traced through source + seed data; not observed
live — no server was booted for this review)

**Evidence:**
- `demo_game/seeds/seed.py:900-921` (`_ARMIES`, `_ARMY_OCCUPIES`): `army_iron_legion` (strength
  **100**, faction `iron_legion`) and `army_city_guard_main` (strength **60**, faction `city_guard`)
  are seeded **already co-located** at `loc_guard_barracks`, both `since_tick=0`. Seeding is
  unconditional — `seed_all()` step 17 (`seed.py:1622-1635`) always runs it.
- `src/npc_engine/graph/military/military_queries.py:148-166` (`get_armies_in_conflict`): matches
  any location with armies from ≥2 factions, **no grace period, no `since_tick` filter**.
- `src/npc_engine/engines/military/military_battle_service.py:90-116` (`_resolve_one_battle`):
  picks the higher-strength faction as winner and calls `set_controls_location` **unconditionally**,
  before any check on whether the loser's army survives. Iron Legion (100) beats City Guard (60)
  deterministically on the very first evaluation — there is no randomness and no player lever: no
  API route anywhere reinforces, weakens, or moves an army (`grep -rn army src/npc_engine/api/routes/`
  returns nothing; `set_army_strength` in `military_writer.py:200` is called only from inside the
  battle resolver itself).
- `src/npc_engine/scheduler/tick_scheduler.py:344-368` (`_ordered_tick_engines`): the military
  engine runs on **every** `advance()` call with no interval gate — unlike gossip/event, which use
  configurable `gossip_interval`/`event_interval` (`tick_scheduler.py:204-205`), military has none.
- `demo_game/world_objectives.py:37-38`: `DEMO_LOSE_LOCATION_ID = "loc_guard_barracks"`,
  `DEMO_LOSE_FACTION_ID = "iron_legion"` — exactly the location/faction the seed pre-arranges for
  Iron Legion to win.
- `demo_game/game_end_checker.py:314` (`_select_failure`) checks `legion` first and, per its own
  docstring (`:300-301`), the legion/bankruptcy/overreach lose paths **unconditionally override any
  win** that may have already fired the same tick.
- `demo_game/pollers/game_end_poller.py` polls every 3s and `demo_game/ui/layout/game_window.py:591-593`
  latches `self._game_over = True` **permanently** the first time `outcome is not None`, then draws a
  game-over overlay every frame from then on.
- The trigger is not player-gated: `src/npc_engine/config.py:269-270` —
  `TICK_AUTOPILOT_ENABLED: bool = True`, `TICK_INTERVAL_SECONDS: int = 10` — and
  `src/npc_engine/main.py:216-224` starts the autopilot task at app boot. Only
  `docker-compose.freeze.yml:31` overrides it to `false` (for eval measurement, per DEC-259); the
  ordinary demo compose file does not. So on a stock `make docker-up && make demo-seed`, the server
  autopilot-ticks the clock every 10 seconds **independent of any player action** — the battle (and
  the permanent loss latch) resolves on the first such tick, plausibly before a player has typed
  anything.
- Even in the scripted 5-minute run, the very first `advance_clock` call is `tick_1`
  (`demo_game/runners/run.py:137`, `delay_before_ms=1000`) — used for Act-1 gossip — long before the
  intentional "Act 5 — Military engine" reveal beat the script stages at **T+4:20**
  (`docs/DEMO_SCRIPT.md:19,66-69`). The battle the script frames as a late-game reveal actually
  resolves ~1 second in.
- `demo_game/constants.py:257` (`DEADLINE_TICKS = 40`) is commented "At 1 auto-tick per real-world
  second this gives ~40 s; adjust for balance" — confirming the intended play window is on the order
  of 40 seconds of ticking before *any* lose condition should plausibly fire. The legion lose fires
  roughly 40× earlier than the game's own balance comment assumes.

**Why it matters:** Win requires ≥2 factions at standing ≥50 (starting standing is 0 for all three),
or 500 gold (starting gold is 60), or 3 of 11 quest-chain quests completed, or a signed treaty — all
of which need many ticks and many dialogue/quest/trade interactions to build. Lose-by-legion requires
zero player action and fires on the first tick the server (or player) ever advances. A studio
evaluator who boots the stack with defaults, or who plays freely for even a few seconds, will see
"GAME OVER — LOSE" almost immediately, and the UI never un-latches it. This breaks the core loop the
demo is built to sell and directly contradicts the "win AND lose reachable" attestation in the prior
review's §4.
**Already known:** No — not found in `ISSUES.md`, `archive/ISSUES_RESOLVED.md`, or
`review-2026-08/{FINDINGS,TRIAGE}.md` (grepped `military`, `iron_legion`, `barracks`, `battle`,
`win`/`lose`; the only hits were an unrelated stale import path, `ISSUE-204`, and unrelated
`_LOGGER`-naming gaps in `military_*.py` files, `ISSUE-296`).
**Fix sketch:** Pick one (or combine): (a) give `MilitaryEngine` a cadence gate like
gossip/event's `*_interval`, tuned so the first battle can't resolve before, say, tick 15-20; (b)
seed the armies with a delayed `since_tick` / a scripted trigger event (mirroring how
`northern_war_begins` is a deliberate `PUT /v1/graph/nodes/world_state` beat, not a seed-time fact)
so the conflict only exists once Act 5 stages it; (c) add a player-facing lever (a quest or trade
action that reinforces `army_city_guard_main`) so the outcome isn't purely deterministic-lose; (d) at
minimum, set `TICK_AUTOPILOT_ENABLED=false` in the demo's own compose override the same way
`docker-compose.freeze.yml` does, so a booted-but-idle stack doesn't lose the game for the player
before they arrive.

### [L6-02] ISSUE-107's "wired into the e2e battery" claim is false — the cross-session memory scenario never runs automatically
Severity: MEDIUM · Confidence: Confirmed

**Evidence:** `e2e/scenarios/scenario_memory_recall_e2e.py` implements the two-session recall
scenario the resolution describes, but defines only a bare `run()` function invoked from
`if __name__ == "__main__":` (file tail) — **no `test_*` function**, no `pytest.mark`. `make scenarios`
(`Makefile:483`) runs `pytest e2e/scenarios/ ... -m "not llm_eval"`, which collects nothing from this
file (pytest only collects `test_*`/`Test*` by default). `grep -rl scenario_memory_recall_e2e .`
(excluding `.git`) returns only the file itself and
`project-harness/archive/ROADMAP_pre-remediation_2026-08-28.md`, which records it was "written" —
never that it was wired to run. No other Makefile target or CI workflow references it.
**Why it matters:** This is the exact "asserted-not-measured" pattern named in both prior reviews'
systemic-pattern lists: the ledger says FIXED, the capability the fix was meant to *prove* runs zero
times in any automated path, so a real regression in cross-session memory recall would currently go
undetected forever.
**Already known:** Not found under this framing in `ISSUES.md` or `review-2026-08/{FINDINGS,TRIAGE}.md`
(closest is `demo_game/tests/beats/test_remembers_you_beat.py`, but that only unit-tests a mocked
`RemembersYouBeat` scene — it never calls the real API, so it doesn't substitute for the e2e scenario).
**Fix sketch:** Rename `run()` to `test_memory_recall_e2e()` (or wrap it), add
`@pytest.mark.e2e`/whatever marker `make scenarios` expects, and confirm it's picked up by
`pytest e2e/scenarios/ -v -s -m "not llm_eval" --scenarios-only`. Needs a live stack, so gate it the
same way the rest of `e2e/scenarios/` is gated (`--scenarios-only`).

### [L6-03] The entire "branch" system is one two-option stub, undocumented as final scope
Severity: MEDIUM · Confidence: Confirmed

**Evidence:** `demo_game/branches/branch_node.py:89-91` labels its content
`"First-slice authored content — garrick_deserter spare/turn-in branch"`. Searching all of
`demo_game/` (excluding tests) for `BranchNode(` construction finds exactly one production call site:
`build_garrick_branch()` (`branch_node.py:116-133`) — two options, each applying a single
`RepDeltaEffect` (a flat reputation delta to one faction). `demo_game/runners/run_scenes.py:629-650`
(`BranchBeat`) is the only place a branch is ever presented, and it always renders this same node.
No second branch exists anywhere in `demo_game/`, `seeds/`, or the eval-world seeders. No
`DECISIONS.md` entry documents "slice 1 is the final scope" (grepped `H2.8`, `BranchNode`,
`branch_node`, `garrick` — zero hits in `DECISIONS.md`).
**Why it matters:** "Branching" is one of the capabilities the product pitch leans on (H2.8 exists as
a named milestone). A studio evaluator who finds the branch panel will see one binary choice with a
single numeric side-effect each — thin enough to read as a tech-demo stub rather than a system, and
there's no ledger record saying that's deliberate rather than abandoned mid-slice.
**Already known:** No.
**Fix sketch:** Either author 1-2 more `BranchNode`s (different effect types — e.g. one that also
calls `WorldStateEffect`, mirroring `branch_effects.py:110`'s existing `put_world_state` hook — to
show the primitive is general, not garrick-specific), or add a `DECISIONS.md` entry stating slice-2
is deliberately out of scope for this milestone so it stops reading as an oversight.
