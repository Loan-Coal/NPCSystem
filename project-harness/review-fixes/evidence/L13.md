## C. Gather / bounding inventory

Repo-wide (`grep -rn "asyncio.gather" src/ demo_game/`, excluding tests) there are **exactly three
`gather` sites**, and none is an unbounded N-way fan-out:

| Site | Shape | Bound |
|---|---|---|
| `engines/agenda/intent_formation_engine.py:115` | fan-out over NPC×player pairs | **bounded** — `Semaphore(settings.MAX_CONCURRENT_TICKS)` at `:106`, and the input list is already `capped` |
| `engines/memory_consolidation/memory_consolidation_engine.py:215` | one coroutine per eligible NPC | **bounded** — `Semaphore(settings.MAX_CONCURRENT_TICKS)` at `:214` |
| `engines/chapter/chapter_engine.py:229-236` | nested `gather(gather(a,b), gather(c,d))` | **fixed arity 4** — four constant repository reads, not a fan-out |

**Correction to the brief's premise.** Chapter's "3 nested gathers" is a fixed 4-way concurrent
read of `get_recent_events_for_chapter`, `get_completed_quests_since_tick`, `get_world_state` and
`get_faction_standings_summary`. It cannot grow with NPC count. And *both* genuine fan-out sites
are semaphore-bounded. **There are zero unbounded gathers in the repo. This is not the load
problem.** The load problem is the opposite shape — see §D.1.

The one real concern here is that `MAX_CONCURRENT_TICKS=20` bounds `memory_consolidation` at **20
simultaneous LLM generations against a single resident model**. "Bounded at 20" is not a meaningful
bound when the backend has one model slot and no queue (L13-06).

## D. Load analysis

### D.1 Sequential per-entity round-trips — the real fan-out

20 of 27 tick engines contain `for <entity> in <working set>: await <repo>.<op>(...)` — a serial
Neo4j round-trip per entity, per tick, with no batching. Worst by awaits-per-iteration:

| Engine | Awaits per iteration | Site |
|---|---|---|
| `mood_contagion` | 7 (`store.get`×2, `store.set`×2, `set_character_mood`×2, +) | `mood_contagion_engine.py:93-108` |
| `gossip` `_run_side_effects` | up to 6 (`create_rumor`, `believe_rumor`, `apply_event_shock`, `log_gossip`, `refresh_embedding_safely`, `propagate_secret`) | `gossip_handler.py:310-372` |
| `clique` | 4 | `clique_formation_engine.py:83-112` |
| `faction_politics` | 2–3 | `faction_politics_engine.py:83-90`, `:185-192` |
| `routine` | 2 | `routine_engine.py:71-92` |
| `quest_generation` | 1 **LLM call**, looped `_MAX_RETRIES` times | `quest_generation_engine.py:219-220` |

`gossip_handler.py` documents itself as *"a single batch read … and a single batch write"*
(`:120`) — true of the propagation, immediately undone by the serial side-effect loop.
**Measured: the gossip tick cost 24.25 s wall-clock with zero LLM calls** (L13-07).

### D.2 LLM serialisation and the interactive turn

`grep -rn "Semaphore\|asyncio.Lock\|queue" src/npc_engine/engines/llm/*.py` → **no matches**.
There is no client-side queue, no admission control, no priority, and nothing anywhere that
distinguishes a player's dialogue turn from background tick work. Both reach the same Ollama
instance holding the one resident `qwen2.5:7b`.

Worst-case model calls in a single background tick, derived from the shipped caps:

| Source | Cap | LLM calls |
|---|---|---|
| `event_quest_trigger` | `_MAX_EVENTS_PER_TICK = 10` (`:30`) × `_MAX_RETRIES = 3` (`quest_generation_engine.py:50`) | 30 sequential |
| `need_quest_trigger` | `_MAX_NEEDS_PER_TICK = 10` (`:27`) × 3 | 30 sequential |
| `world_state_quest_trigger` | `DEFAULT_MAX_PER_TICK = 1` (`:39`) × 3 | 3 sequential |
| `chapter` (on transition) | 1 | 1 |
| `memory_consolidation` | 1 per active NPC, `Semaphore(20)` | up to 20 **concurrent** |
| **Total** | | **64 sequential + up to 20 concurrent ≈ 84** |

This independently confirms L11's ~86 from the scheduler side. Costed against DEC-273's measured
decode (warm free-text 1.31 s / 54 tok; warm structured dialogue 3.5–4.2 s / 127–162 tok — decode
is ~97% of the turn, so cost scales with output tokens, not prompt size):
**64 sequential calls ≈ 84 s at the small-output end, ≈ 220 s (3.7 min) at dialogue-sized output.**
Live anchor from this run: `memory_consolidation.last_duration_ms = 3202.6` for **one** NPC.

**What happens to a player's dialogue turn that arrives mid-tick.** Nothing protects it. It queues
behind whatever the tick has already handed the backend, with no priority and no pre-emption.
`LLM_TIMEOUT_SECONDS=60.0`, so the turn either returns tens of seconds late or trips the timeout
and degrades `full → graph_only → canned`. DEC-273's 3.5–4.2 s warm figure was measured against an
otherwise idle backend and **only holds while the world is idle**. That is the single most
important fact in this lens: the measured dialogue budget is a best case that the engine's own
background work routinely destroys, and nothing in the system notices.

# Findings

### [L13-01] The demo seed writes no `:Schedule` nodes, so `routine` can never move an NPC — and four co-location engines are silently starved behind it
Severity: HIGH · Confidence: Confirmed
**Evidence:**
- `graph/scheduling/routine_queries.py:26` — `MATCH (c:Character)-[:FOLLOWS_SCHEDULE]->(s:Schedule) WHERE c.is_active = true`.
- `grep -rn "Schedule\|FOLLOWS_SCHEDULE" demo_game/seeds/*.py` → **no matches**. The seed creates no `:Schedule` node and no `FOLLOWS_SCHEDULE` edge.
- Live label census of the seeded eval world — no `Schedule` label present: `Belief 29, Memory 29, Need 28, Quest 18, Character 15, Goal 15, Secret 14, Location 11, FactionStandingEvent 10, Faction 6, Event 4, Item 2, Leverage 2, Army 2, WorldState 1, Chapter 1, QuestState 1`.
- Live: `routine` returns `{'moved': 0, 'skipped': 0}` on every tick. `skipped` is 0 **too**, so the query returned zero rows — not "no schedule entry matched this time of day".
- Downstream readers of the `LOCATED_AT` that `routine` would have written, all returning empty: `mood_contagion` `{'affected': 0}`, `proactive_dialogue` `{'proactive_lines': []}`, `player_model` `{'player_models': []}`, plus `need_decay`'s satisfier join (`need_queries.py:96-97`).

**Why it matters:** NPCs never move in the shipped demo world. Every engine whose whole purpose is
"NPCs in the same place react to each other" — mood contagion, proactive dialogue, the player model
— is permanently starved by a missing seed edge, and each reports `0` in a way indistinguishable
from a quiet world. This is the 2026-06 review's "asserted-not-measured" pattern in its purest
form: the engines are unit-tested against fixtures that supply schedules; the live world supplies
none.

**Fix sketch:** Add `:Schedule` nodes and `FOLLOWS_SCHEDULE` edges to `demo_game/seeds/seed.py`
(the underlying data already exists implicitly in the location / time-of-day design). Add a
seed-time post-check — the shape `make check` can hold — asserting each seeded NPC carries the
edges its readers require. Separately, make `routine` return `scheduled: <n>` alongside
`moved`/`skipped`, so an empty working set is visible rather than inferred.

### [L13-02] 28 `:Need` nodes are orphans — no `HAS_NEED` edge — so `need_decay` and `need_quest_trigger` are both dead, and both report `0`
Severity: HIGH · Confidence: Confirmed · **Already known:** ISSUE-210 / ISSUE-213 — **still live at HEAD, and the blast radius is larger than logged**
**Evidence:**
- `demo_game/seeds/seed.py:1581-1589` creates `:Need` nodes carrying a `character_id` **property** and no edge.
- The only writer of the edge is `graph/needs_goals/need_writer.py:50` (`CREATE (c)-[:HAS_NEED]->(n)`), which the seed does not call — it goes through the generic `_seed_node` admin path.
- Every reader requires the edge: `need_queries.py:33`, `:61`, `:95` all `MATCH (c:Character)-[:HAS_NEED]->(n:Need)`.
- Live relationship census of the seeded world (complete — 13 types returned under `LIMIT 20`): `BELIEVES 29, REMEMBERS 29, PURSUES 15, LOCATED_AT 14, KNOWS_SECRET 14, MEMBER_OF 9, STANDS_WITH 6, KNOWS_ABOUT 6, HAS_QUEST 5, RELATES_TO 2, OWNS 2, HAS_LEVERAGE 2, OPPOSES 1`. **`HAS_NEED` is absent.**
- Live: `need_decay` → `{'needs_updated': 0, 'needs_critical': 0}` on every tick; `need_quest` → `{'quests_created': 0}` on every tick.

**Why it matters:** ISSUE-210 frames this as *"a prompt field that is empty in 100% of rows"* — a
retrieval nuisance, severity P2. It is not: it takes out two whole tick engines. `need_decay`
cannot decay a need, and `need_quest_trigger` cannot fire, so the entire needs-driven quest
pipeline is inert in the shipped demo world and always has been. ISSUE-213's label fix appears to
have landed (the label is now `Need`, not `need`), which makes this the "DONE overstated" pattern:
the label half shipped, the edge half did not, and the entry now reads as partially resolved while
the subsystem is still fully dead.

**Fix sketch:** Route the seed's need creation through `need_writer.create_need` instead of
`_seed_node`, or write the `HAS_NEED` edge explicitly. Then gate it: a seed-integrity check that
every label the type registry declares as edge-required actually carries its edge after a seed run
— the same check would have caught L13-01. Re-scope ISSUE-210's severity; P2/cosmetic is wrong.

### [L13-03] `military` reports `battles_resolved: 1` on every single tick, forever, while its docstring calls it a no-op stub
Severity: MEDIUM · Confidence: Likely
**Evidence:** Live, on ticks 9, 10, 11, 12 and every sampled tick: `military` →
`{'battles_resolved': 1, 'factions_yielded': 0}`. The world holds exactly 2 `:Army` nodes and the
count never changes. `military_battle_service.py:71-73` resolves one battle per contested location
per tick, and the return payload carries only a count — no battle id, no settled marker.
`tick_scheduler.py:129` still documents this engine as *"currently a no-op stub (see ISSUES.md
ISSUE-001)"*. `last_duration_ms: 46.3` makes it one of the more expensive engines in the tick.

**Why it matters:** Either the same battle is re-resolved every tick — a non-idempotent write,
invisible because the payload reports only a count — or a battle genuinely resolves every tick and
the demo world is in permanent unchanging war. Both are wrong, and the stale "no-op stub"
docstring means nobody would think to look.

**Fix sketch:** Have `_resolve_one_battle` return the battle id and mark the contest settled so
re-resolution is impossible; report the ids alongside the count so "one new battle" and "the same
battle again" are distinguishable in the payload. Correct the `tick_scheduler.py:129` docstring in
the same change.

### [L13-04] `engine_status` is exposed on two endpoints, read by nothing, and structurally cannot express "starved"
Severity: HIGH · Confidence: Confirmed
**Evidence:**
- The record is complete and useful: `EngineStatusRecord` carries `last_tick_id`, `last_error`, `last_error_tick`, `error_count`, `last_duration_ms`, `tick_count` (`scheduler/engine_status_store.py`), populated at `tick_scheduler.py:225-241` via `EngineTickTimer`.
- Surfaced at `api/routes/admin/system.py:98-109` (`GET /v1/admin/system/engines`) and `api/routes/world/clock.py:131`.
- Nothing consumes it. `grep -rn "engine_status\|last_error\|error_count" src/npc_engine/api/` returns only the wiring and those two read routes. No metric, no health-check integration, no gate. `GET /health` returned `{"status":"ok","version":"8d30a3e1"}` throughout and would do so with every engine erroring.
- It also cannot express the failure this lens actually found: `error_count: 0`, `tick_count: 7` and a non-null `last_duration_ms` are identical for a healthy idle engine and for one whose working-set query returns zero rows forever (L13-01, L13-02).

**Why it matters:** The design intent — isolate engine failures so one bad engine cannot halt the
tick — is sound, but it converts a loud crash into a silent absence with no compensating signal.
An engine can be dead for weeks and the only place that says so is an admin endpoint nobody polls.
For the two worst cases in this census, even that endpoint reads green.

**Fix sketch:** Two cheap changes, and the second is the load-bearing one. (1) Export
`engine_last_error_tick` / `engine_error_count` as gauges on `GET /v1/admin/system/metrics`, next
to the DEC-273 LLM metrics, so `last_error` lands where the latency work already put its signal.
(2) Add `working_set_size` (or a `worked` boolean) to the status record, set by the scheduler from
the engine's return payload, so "ran and did nothing because there was nothing to do" is
distinguishable from "ran and did nothing because its query matches nothing". Without (2), (1)
would not have caught L13-01 or L13-02.

### [L13-05] `TICK_LLM_CALLS_PER_MINUTE_MAX` counts ticks not calls, gates 2 of the 5 LLM engines, and is entirely absent from the recommended clock mode
Severity: CRITICAL · Confidence: Confirmed
**Evidence:**
- `config.py:272` — `TICK_LLM_CALLS_PER_MINUTE_MAX: int = 6`. Wired at `main.py:222` into `TickBudgetGuard`, enforced at `tick_autopilot.py:85-102`.
- **Wrong unit.** `tick_budget_guard.py:76-83` — `record_llm_tick()` appends **one** timestamp per tick regardless of how many model calls that tick made. A tick making 84 calls (§D.2) costs the budget exactly 1. The setting's name is a lie about its unit.
- **Wrong coverage.** `grep -rn "skip_llm_engines" src/` → the flag is read at exactly two sites: `tick_scheduler.py:467` (`chapter`) and `:535` (`memory_consolidation`). The three quest triggers run at `:472` inside the ungated `_ordered_tick_engines()` list, and are 63 of the 84 worst-case calls. **Load-shedding removes 25% of the calls and leaves 75%.** Independently confirms L11.
- **Wrong entry point.** `tick_scheduler.py:552` — `advance(..., skip_llm_engines: bool = False)`. `api/routes/world/clock.py`'s `advance_clock` never passes it; `grep -rn "skip_llm_engines" src/npc_engine/api/` → **no matches**. Only `tick_autopilot.py:98` supplies it. `ENGINES.md:29-31` calls `game_driven` the *"recommended"* mode. The eval stack runs exactly that (`CLOCK_MODE=game_driven`, `TICK_AUTOPILOT_ENABLED=false`), so the guard was never constructed during any measurement in this document.

**Why it matters:** This is the one mechanism in the system meant to stop background work from
eating the interactive model, and all three of its axes are broken. A studio reading the setting
name reasonably concludes background LLM work is capped at 6 calls/minute. The real ceiling in
`game_driven` mode is **unbounded**; even in `realtime` mode it is 6 *ticks* × up to 84 calls ≈ 500
calls/minute against one 7B model. This is directly against the standing small-model goal: shedding
background load under interactive pressure is the highest-leverage lever available and it is
currently disconnected.

**Fix sketch:** Three separable steps, in value order. **(3) first** — extend `skip_llm_engines` to
cover the three quest triggers. It is a five-line change and converts a 25% shed into a 100% shed.
(1) Move the gate from the autopilot into `TickScheduler.advance()` so both clock modes get it, and
have `advance_clock` pass through. (2) Increment the guard per **call** rather than per tick — the
seam already exists, since DEC-273's `llm_backend_calls_total` counter sits at exactly the right
place — and reconcile the setting's name with its unit.

### [L13-06] No queue, no priority and no admission control in front of the single resident model — a background tick can push a player's turn past its 60s timeout into `canned`
Severity: CRITICAL · Confidence: Confirmed
**Evidence:**
- `grep -rn "Semaphore\|asyncio.Lock\|queue" src/npc_engine/engines/llm/*.py` → **no matches** across `ollama_adapter.py`, `factory.py`, `protocols.py`, `openai_adapter.py`, `ollama_payload.py`.
- Nothing distinguishes an interactive call from a background one. DEC-273's `engine` metric label is the only per-caller signal and it is purely observational.
- `memory_consolidation_engine.py:214` fans out up to `MAX_CONCURRENT_TICKS` (20 on the eval stack) simultaneous generations at the backend.
- DEC-273 established there is **one** resident model: *"`qwen2.5:14b` (10.24 GB) still evicts `qwen2.5:7b` (5.38 GB) on this card … Only one model fits."*
- `LLM_TIMEOUT_SECONDS=60.0` on the eval stack; dialogue degrades `full → graph_only → canned` on timeout.
- Measured live: a single tick containing one consolidation cost **3.2–5.7 s** wall-clock (`memory_consolidation.last_duration_ms: 3202.6`, for one NPC). §D.2 derives 64 sequential + up to 20 concurrent calls in the saturated case, ≈ 84 s–220 s.

**Why it matters:** DEC-273's headline — warm dialogue at 3.5–4.2 s against a 3–7 s budget — was
measured against an idle backend. It is a best case, not a guarantee, and nothing in the system
preserves it under load. The observable failure for a player is a turn that either arrives tens of
seconds late or silently downgrades to a canned line, and that downgrade currently has no
attributable cause in any log, because contention is not measured. On the small-model goal this is
the central mechanism: the reason a small local model looks bad is not the model, it is that the
game's own background work is queued in front of the player.

**Fix sketch:** Add a two-class admission gate in the LLM layer — a semaphore with a slot reserved
for the interactive class (or a small priority queue), where `dialogue` always pre-empts
tick-originated work and tick-originated calls are *shed* rather than queued while the interactive
class is active. The `engine` label from DEC-273 already carries the class distinction, so
classification costs nothing. Pair with L13-05(3) so the shed actually reaches the quest triggers.
Instrument `llm_backend_queue_wait_seconds` alongside the existing latency histogram, so contention
becomes visible before it becomes a support ticket.

### [L13-07] The gossip tick costs 24.25s wall-clock with zero LLM calls — a full corpus reconciliation runs once per propagated pair inside a serial loop
Severity: HIGH · Confidence: Confirmed
**Evidence:**
- Measured live: the tick landing on `GOSSIP_TICK_INTERVAL=10` took **24,252 ms**; the five surrounding non-gossip ticks took 433, 455, 486, 493 and 570 ms. Payload: `{'tick_id': 10, 'pairs': 20, 'propagated': 10}`.
- `gossip` is not an LLM engine — `grep "uses_llm: true" src/npc_engine/engines/contracts/*.yaml` returns only `chapter_engine`, `dialogue_engine`, `memory_consolidation_engine`, `quest_generation_engine`.
- The cost is in `_run_side_effects` (`gossip_handler.py:310-372`): a serial `for` loop over propagated pairs issuing up to 6 awaits each, including `refresh_embedding_safely` at `:359`.
- That call reaches `retrieval/embedding/corpus_refresher.py:52-62` → `retrieval/embedding/corpus.py:266` — `await reconciler.reconcile_in_session(session)`, **a full reconciliation pass, per pair**. Ten propagated pairs run ten reconciliation passes in one tick, sequentially, each re-embedding via `EMBEDDING_MODEL=all-MiniLM-L6-v2` on the same GPU as the resident LLM.
- The handler's own docstring at `:120` claims *"a single batch read … and a single batch write"* — true of the propagation, false of the tick.

**Why it matters:** 24 s is roughly 6× the entire interactive dialogue budget, it recurs on a fixed
cadence, and because it is not LLM work none of the budgeting in §D.3 would ever shed it. It also
contends for the same GPU as the resident model, degrading interactive dialogue by a path DEC-273
did not instrument. This is the largest single measured cost in the tick and nothing in the repo
mentions it.

**Fix sketch:** Hoist the reconciliation out of the per-pair loop — one `reconcile_in_session` per
tick, after the loop, then upsert the affected node ids in a batch. `refresh_corpus_node` already
separates the two halves (`corpus.py:266-270`), so this is a restructuring, not a redesign; it
turns 10 passes into 1. Then batch the remaining per-pair writes (`create_rumor` / `believe_rumor`
/ `log_gossip`) the way the propagation write already is. Add a wall-clock ceiling assertion on the
gossip path — `last_duration_ms` is already recorded per engine, so the gate has its input for
free.

### [L13-08] Two unbounded appenders nobody has logged: `:TickLease` nodes and the `SchedulerState` tick-id array property
Severity: MEDIUM · Confidence: Confirmed · **Related:** ISSUE-279 (same retention gap, different nodes)
**Evidence:**
- `graph/scheduling/tick_lease_queries.py:20` — `MERGE (l:TickLease {scheduler_id, engine, tick_id})`. One node per engine per interval tick. `grep -rn "TickLease" src/ | grep -iE "delete|prune|remove"` → **no matches**; nothing ever deletes one. `DISTRIBUTED_TICK_LEASE_ENABLED` defaults to **`True`** (`config.py:265`), so this is the default path. ISSUE-277 already counted **3,498** such rows in the live graph, as an incidental observation while investigating something else.
- `graph/scheduling/tick_scheduler_queries.py:20-27` — `mark_tick_done` does `SET s[$key] = completed + $tick_id` on a **single** `:SchedulerState` node, appending one integer per interval tick forever. `is_tick_done` (`:14-17`) then evaluates `$tick_id IN completed` — an O(n) scan of that array on **every** gossip and event tick. No pruning anywhere (`grep -rn "SchedulerState" src/ | grep -iE "delete|prune|trim"` → no matches).

**Why it matters:** ISSUE-279 logs the `:FactionStandingEvent` / `:Event` growth, and I confirm it
is still live (22 → 64 and 6 → 13 respectively across 6 advances this run). These two are the same
class and are not logged. The `SchedulerState` one is the nastier: an ever-growing Neo4j array
property on one hot node, re-read and linearly scanned on every interval tick, so its cost grows
quadratically in uptime rather than linearly. Both poison graph-scale measurement exactly the way
ISSUE-279 does — a census anchor that passes for the first few minutes of uptime and then does not.

**Fix sketch:** Give `:TickLease` a TTL sweep — the node already carries `tick_id`, so
`MATCH (l:TickLease) WHERE l.tick_id < $current - $retention DELETE l` is sufficient, with a
retention window comfortably exceeding `lease_ttl_seconds`. For `SchedulerState`, replace the array
with a high-water mark plus a bounded recent window (the dedup only ever needs to answer "have I
done this tick", and ticks are monotonic) — or delete the local path entirely, now that the
distributed lease is the default. Fold both into ISSUE-279 as one retention story.

### [L13-09] `POST /v1/clock/advance` accepts `delta_ticks: 1000`, running 27 engines 1000 times in one request, on one session, under one lock, with a world-state snapshot frozen at the first tick
Severity: HIGH · Confidence: Confirmed
**Evidence:**
- `config.py:52` — `MAX_DELTA_TICKS: int = 1000`; `api/routes/world/clock.py:37` — `delta_ticks: int = Field(default=1, ge=1, le=MAX_DELTA_TICKS)`.
- `tick_scheduler.py:568-582` — `advance()` reads `world_state = await get_world_state(...)` **once, before** the `for tick_id in range(...)` loop, and passes that same object into every iteration.
- Consequences inside the loop: `routine.run_tick(time_of_day=world_state.time_of_day)` (`:461`) sees a frozen time-of-day for all N ticks; `_maybe_consolidate_memory` (`:538-543`) builds its `TimePoint` from the same pre-loop snapshot.
- The whole range runs inside `async with self._lock` (`:567`) on a single `AsyncSession`, with `skip_llm_engines` false throughout (L13-05).
- At the measured 433–570 ms deterministic floor, 1000 ticks is ≈ 8 minutes of held lock with **no** LLM work at all; with quest triggers firing it is unbounded.

**Why it matters:** The API-boundary input cap is satisfied in form and not in effect — `le=1000`
looks like a cap but admits a single authenticated request that can occupy the scheduler for hours
and issue tens of thousands of model calls, with no timeout and no back-pressure. Separately, the
frozen `world_state` is a correctness bug in its own right: batched advances see a time-of-day that
never changes, so `routine` (once L13-01 is fixed) would move NPCs into the same slot 1000 times.

**Fix sketch:** Re-read `world_state` inside the tick loop, or at minimum recompute `time_of_day`
and the consolidation `TimePoint` per tick. Independently, lower `MAX_DELTA_TICKS` to something a
frame can absorb (single digits); if large catch-up advances are a genuine requirement, make them
an explicit background job with its own budget rather than a synchronous HTTP call.

### [L13-10] No test pins the tick execution order, so every dependency in §A.2 can be broken silently
Severity: MEDIUM · Confidence: Confirmed
**Evidence:** `grep -rn "_ordered_tick_engines" tests/` → no matches. `tests/unit/scheduler/`
contains only `test_engine_tick_timer.py`. `tests/unit/engines/test_tick_scheduler_llm_skip.py`
asserts the skip flag and `chapter_interval`, nothing about ordering. No file under `tests/`
asserts a call order for the scheduler. `ENGINES.md:34-45` promises *"a fixed order so that
upstream state … is visible to downstream engines within the same tick"* — a promise with 12
identified real dependencies (§A.2) and zero gates.

**Why it matters:** `_ordered_tick_engines()` is a hand-maintained list of 22 entries that reads
like arbitrary registration order. Anyone adding an engine will append to it; anyone tidying it
will sort it. Either action silently changes behaviour — an NPC's mood blends against last tick's
location, a quest trigger fires on last tick's need level — and the whole suite stays green. This
is the "invisible coupling with no gate" class exactly, and it is the reason §A.2 had to be
reconstructed by hand rather than read off anywhere.

**Fix sketch:** One test that constructs a `TickScheduler` with recording fakes in all 28 engine
slots, runs a single tick, and asserts the observed call sequence against an explicit expected list
— the same shape as an API-contract baseline, so a deliberate reorder is a one-line diff and an
accidental one is a failure. Then move the §A.2 table into `ENGINES.md` beside the order it
justifies, so the *reason* for each position is written where the next person will edit it.
