## Findings

### [L7-01] `matchers.py`'s `_DISPATCH` table is a closed seam for new eval-scorer kinds
Severity: MEDIUM · Confidence: Confirmed
**Evidence:** `evals/matchers.py:529-543` — `_DISPATCH: dict[str, _Evaluator]` maps 14 kind strings to functions defined earlier in the *same* 544-line file. Every `_eval_*_judge` wrapper (`_eval_tone_judge:237`, `_eval_affirms_judge:258`, `_eval_commits_judge:289`) funnels into the one shared `_run_binary_judge` (`:187`) and the one shared prompt envelope `prompts/eval/tone_judge.yaml`. `DECISIONS.md:2059-2074` (DEC-145) explicitly waives the 300-line module limit for `matchers.py` on the grounds it is "a single cohesive module" — this was a deliberate call, not drift, and the module has since grown from the 474 lines DEC-145 measured to 544.
**Why it matters:** Directly on-axis for "new scorers... in `evals/`" per the review brief. A new deterministic matcher `kind` (e.g. a numeric-range judge, a JSON-path extractor) cannot arrive as a new file; it must be added to the shared dispatch table in a file the project has already flagged as size-pressured. This is the mirror image of the gossip-distortion fix: gossip proved a closed if-chain *can* become a registry across small files; `matchers.py` shows the alternative — a deliberately centralized dispatch table — was chosen instead, and is now the one closed seam among the eval-authoring surfaces (cases and generation are both file-glob open).
**Fix sketch:** If matcher kinds keep growing, split `_eval_*` functions into `evals/matchers/*.py` with self-registration into `_DISPATCH` at import time (mirroring `type_registry`'s glob pattern, or `engines/llm/factory.py`'s explicit-but-centralized pattern) before the file approaches the 800-line hard cap that applies to `src/`. Given DEC-145 was a deliberate choice, this is a **Decide** item, not an auto-fix — log in `DECISIONS.md` only if/when a second contributor needs to add a matcher kind and finds the file a bottleneck.

### [L7-02] `engines/llm/factory.py`'s own docstrings describe a self-registration pattern the code does not use
Severity: LOW · Confidence: Confirmed
**Evidence:** `engines/llm/factory.py:10-13` — "add a new local/remote LLM backend by writing an adapter... and calling `register_backend(...)` at import time, then importing it from `engines/llm/__init__.py` so registration runs on package import." `engines/llm/__init__.py:9-11` repeats this claim, citing "(L7-07)". But the actual registrations are three explicit calls at the bottom of `factory.py:107-109`, and no adapter module (`ollama_adapter.py`, `openai_adapter.py`, `mock_adapter.py`) calls `register_backend` itself. Adding a fourth backend means editing `factory.py` in three places (import line, `_build_x` function, `register_backend` call) — not writing one file and importing it.
**Why it matters:** The docstring overclaims openness by a full tier (open vs. partly-open), which will mislead the next engineer who reads it before adding a backend. It is the mirror twin of the `STRATEGY_REGISTRY` overclaim (L7-06 below) — the codebase has now made this exact overclaim twice, in the two files the 2026-06-03 review's §4 held up as templates.
**Fix sketch:** Either (a) rewrite the docstrings to say "register the new backend by adding one `register_backend(...)` call to this file" (honest, matches the emotion-model-factory docstring's phrasing at `emotion_model_factory.py:1-9`, which does NOT make the self-registration claim), or (b) actually implement self-registration (each adapter module calls `register_backend` at its own module scope, and `__init__.py` imports every adapter module instead of `factory` alone) to make the docstring true. (a) is a one-line-per-file fix; (b) changes the import graph and is the only genuinely OCP-open version of this seam. Not urgent — file it if picked up.

### [L7-03] Adding a new tick-driven engine requires editing 4 existing files, not 1-2
Severity: MEDIUM · Confidence: Confirmed
**Evidence:** See axis 5 above for the precise enumeration and file:line citations. `scheduler/tick_scheduler.py:50-98` alone has 28 named optional `TickEngine | None = None` constructor parameters (one per engine, all added by hand over the roadmap's history); `_ordered_tick_engines()` (`:344-367`) is a 22-entry static tuple list for the "simple" engines. `api/dependencies_engines/engine_slots.py:19-60` duplicates every engine name a second time as `TypedDict` keys. `api/dependencies_engines/__init__.py:98-167` duplicates it a third time across `_core_engine_kwargs()`/`_advanced_engine_kwargs()`.
**Why it matters:** This is the number the review brief asked for directly ("Enumerate them precisely — that number IS the OCP verdict"). Four files, each touched at 1-4 separate points, for what the roadmap treats as a routine, frequent operation (28 engines shipped to date, several per ROADMAP.md phase). This is a real cost, but it is not free-floating debt: `_assert_every_engine_slot_wired` (`dependencies_engines/__init__.py:186-201`) derives its expected-slot set from `TickScheduler.__init__`'s own signature via `inspect.signature` (not a hand-copied list), so a slot added to `tick_scheduler.py` and forgotten in the composition root now fails loud (`EngineWiringError`) instead of silently no-opping — this appears to be a fix for `CR-L01-09` ("No composition-root assertion that every tick engine slot is filled (27 registered, 4 tested)", `review-2026-08/FINDINGS.md:90`) and `CR-L01-03` ("`memory_consolidation_engine` never passed... has never run", `FINDINGS.md:84`) — both UPHELD as of the 2026-08-28 baseline, both appear FIXED on HEAD (`memory_consolidation_engine` is present in `_advanced_engine_kwargs()` at `__init__.py:127`, and the guard now exists). **Note for the synthesis pass:** verify this against L1's re-check of CR-L01-03/09 before crediting it as fixed twice.
**Fix sketch:** Not proposing a fix — 28 engines with heterogeneous call signatures (`tick_id` vs. `time_of_day` vs. `game_time`) is a case where a fully generic plugin registry (e.g. a single `list[TickEngine]` plus a name→interval mapping) would trade this explicitness for a subtler bug class (order-dependent side effects across 28 engines becoming implicit). The `_ordered_tick_engines()` extraction already did the safe 80% of that refactor (22 of 28 engines share one call shape and now live in one declarative list rather than 22 duplicated `if x is not None: row = await...` blocks). Flag as a **Decide** item only if a new engine family with a *fifth* distinct call signature is added — that is the point where the special-cased engines (gossip/event/routine/chapter/story_pacing/consolidation) start to dominate and the abstraction should be revisited.

### [L7-04] Location-connection `kind` is still an unconstrained `str`, not `Literal`/`Enum`
Severity: LOW · Confidence: Confirmed
**Evidence:** `api/routes/world/location_graph.py:36` — `kind: str = Field(..., description="Connection type: road | river | sea | secret")`. The four values are documented only in a free-text description; the field accepts any string, silently.
**Why it matters:** This is the un-remediated half of the archived L7-04 ("Location graph raw dict + stringly `kind`") — the location-hierarchy blocker (`location_writer.py` absence) it was filed alongside is fixed (see L7-02 re-verification above), but this specific typing gap was never separately tracked and survives untouched. Violates the CLAUDE.md strict rule directly: "No raw `dict`, no raw strings for fixed value sets — `Literal` or `Enum`." A typo'd `kind` (e.g. `"raod"`) passes validation and is only ever caught, if at all, by whatever reads the property later.
**Fix sketch:** `kind: Literal["road", "river", "sea", "secret"] = Field(...)`. One-line change; add a regression test asserting an invalid `kind` 422s. Not logging a fresh ISSUE — this is small enough to fix inline if anyone touches this route next, or log at that time.

### [L7-05] `TraitReadPort`/`TraitModulatedEmotionModel` — the emotion-model OCP seam is open in name only for per-NPC variation
Severity: MEDIUM · Confidence: Confirmed · **Already known: cross-ref `L2-01`** (this same review, different lens — DIP framing)
**Evidence:** `engines/emotion/emotion_model_factory.py:92-95` registers two models (`vad`, `trait_modulated`) — the model-*selection* axis is genuinely open (axis 3 above). But `api/dependencies_stores.py:65-79`'s `get_emotion_updater()` builds `EmotionUpdater(...)` without ever passing `trait_reader`, so `EmotionUpdater._get_model_for` (per `engines/emotion/emotion_updater.py:56,76`) always falls back to the shared, non-trait model — `TraitReadPort` (`engines/ports/trait_read_port.py:17`) has zero implementors anywhere in `src/`.
**Why it matters, from the OCP angle specifically:** `archive/ISSUES_RESOLVED.md:1444-1454` closes ISSUE-096 ("trait-modulated emotion uses global demo-default traits, not per-NPC traits") as FIXED on 2026-06-19, citing the addition of `TraitReadPort` + the optional `trait_reader` param + per-call model building. That addition is real and is a legitimate DIP injection point (2+ implementors not required to add the seam — constructor injection is correct per `npc-coding-principles`). But *as an OCP axis* — "can a new emotion behavior arrive as a new file" — the honest answer for the per-NPC-data half is **no, and worse: the seam that would make it yes already exists and is simply never connected.** Writing `Neo4jTraitReadRepository` as a new file today would still require editing `api/dependencies_stores.py` to pass it in — so even the "fixed" mechanism is at best partly-open, and until that one edit happens, the whole per-NPC-trait axis is dead code with a closed door in front of it.
**Fix sketch:** As L2-01 states — implement `Neo4jTraitReadRepository` and wire it in `api/dependencies_stores.py`, or delete the port/parameter/branch and log the deferral honestly in `ISSUES.md` rather than leaving ISSUE-096 marked FIXED for a behavior that has not changed in production. Deferring to L2's fix sketch to avoid duplicate remediation work.

### [L7-06] `distortion_strategy.py`'s `registry_keys()` docstring overclaims — adding a strategy still edits this module
Severity: LOW · Confidence: Confirmed
**Evidence:** `engines/gossip/distortion_strategy.py:54-64` — `registry_keys()`'s docstring: "Reflects strategies registered after import so a new strategy file is reachable **without editing this module**." But `STRATEGY_REGISTRY` (`:47-52`) is a static dict literal populated by 4 explicit imports at the top of this same file (`:16-19`); no strategy file self-registers. A 5th strategy requires adding both an import line and a dict entry to `distortion_strategy.py`.
**Why it matters:** Same failure mode as L7-02 — the docstring describes the aspirational fully-open version of the pattern, not the partly-open version actually shipped. Low severity because the axis is still a large, real improvement over the old 3-place if-chain (L7-01 re-verification, HOLDS as fixed) and the overclaim is confined to one function's docstring, not a load-bearing contract.
**Fix sketch:** Reword to: "Live view of `STRATEGY_REGISTRY` at call time, in registration order. Adding a strategy still requires one import + one dict entry above; this function exists so callers never hardcode key order separately." One-line docstring fix.

## Small-model relevance

`engines/gossip/` remains the strongest in-repo precedent for a deterministic, no-model implementation of something that looks like it needs a model (distortion "voice", selected and shaped entirely by a `sha256`-seeded index into a registry, with prefix text sourced from YAML — zero LLM calls, `gossip_distort.py:220-260`). No axis surveyed here shows a *closed* seam actively forcing new work onto the LLM that a deterministic new file could absorb instead — the two LLM-adjacent axes (new backend, new engine) are gated by registration-edit friction, not by an architectural requirement that new behavior be phrased as a prompt. The nearest thing to a negative finding on this axis is L7-03: 28 tick engines is a lot of scheduler wiring for what is, per `engines/contracts/*.yaml`, only 6 LLM-calling engines — the deterministic-engine count already dwarfs the LLM-engine count, which is the right shape for the standing goal even though the wiring cost to add either kind is identical.
