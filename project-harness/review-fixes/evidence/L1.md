## Findings

### [L1-01] `/ws/dialogue` has no throughput rate limiting — only a concurrency cap

Severity: HIGH · Confidence: Confirmed

**Evidence:** `RateLimitMiddleware` and `ApiKeyMiddleware` are both `starlette.middleware.base.BaseHTTPMiddleware`
subclasses (`api/rate_limit.py:64`, `auth/middleware.py:50`). Read `.venv/Lib/site-packages/starlette/middleware/base.py:102`:
`if scope["type"] != "http": await self.app(scope, receive, send); return` — for a `"websocket"`
scope, `dispatch()` (and therefore the entire token-bucket check) is **never invoked**. This is
confirmed independent of any test: it is how Starlette's `BaseHTTPMiddleware.__call__` is written.
`api/routes/dialogue/dialogue_ws.py:205-227` performs its own auth check
(`resolve_scope_from_authorization`) and its own **concurrency** cap
(`MAX_WS_CONNECTIONS_PER_KEY = 5`, `_acquire_ws_slot`), but nothing bounds how many times per
second a single valid key may open a new connection, run one LLM-backed turn
(`_run_first_turn` → `handler.handle(request)`, an Ollama call), and disconnect. `RateLimitMiddleware`
also exempts nothing else for WS — it simply cannot see the scope at all.
**Already known:** none found — grepped `ISSUES.md`/`archive/ISSUES_RESOLVED.md` for
"websocket.*rate", "rate.*ws", no hits; not present in `review-2026-08/FINDINGS.md` either
(no lens targeted the WS endpoint specifically).
**Why it matters:** the dialogue WS path is the single most expensive request in the system (one
LLM generation per connection) and the standing goal is minimizing what a small local model must
do / protecting its latency budget. A valid single key can open-generate-close in a loop with no
per-second throttle, unmetered — the same "unmetered LLM amplification" class SEV-20 fixed for
concurrent connections, reopened for connection *rate*.
**Fix sketch:** add a lightweight per-key token bucket inside `dialogue_ws()` (reuse
`_TokenBucket` from `api/rate_limit.py`, keyed the same way as `_active_ws_connections`) checked
alongside `_acquire_ws_slot`, before `websocket.accept()`.

### [L1-02] `API_KEY_GRAPH_WRITE` / `API_KEY_GRAPH_ADMIN` have no weak-secret validation, unlike `API_KEY_SECRET`

Severity: MEDIUM · Confidence: Confirmed

**Evidence:** `config.py:90-92`:
```python
API_KEY_SECRET: str
API_KEY_GRAPH_WRITE: str | None = None
API_KEY_GRAPH_ADMIN: str | None = None
```
Only `API_KEY_SECRET` has a `field_validator`/`model_validator` (`config.py:404-408`,
`:395-401`, delegating to `check_api_key_secret` — min length 16, blocks placeholders, blocks
the shipped dev secret outside dev). Grepped `config.py` and `config_validators.py` for
`API_KEY_GRAPH_WRITE`/`API_KEY_GRAPH_ADMIN` — zero validator references. `auth/api_key.py:69-73`
grants `SCOPE_GRAPH_ADMIN`/`SCOPE_GRAPH_WRITE` (the two highest-privilege scopes — admin inherits
write, per `auth/permissions.py:15-18`) via `secrets.compare_digest(token, settings.API_KEY_GRAPH_ADMIN)`
with no length/placeholder floor on the configured value.
**Already known:** none — grepped `ISSUES.md`/`archive/ISSUES_RESOLVED.md` for
`API_KEY_GRAPH`, zero hits.
**Why it matters:** an operator who sets `API_KEY_GRAPH_ADMIN=admin` (or any short/weak value) in
staging/prod gets no startup rejection, unlike the equivalent mistake on `API_KEY_SECRET`. Since
`API_KEY_GRAPH_ADMIN` grants the same top scope `API_KEY_SECRET` does (`resolve_scope_from_authorization`
falls through to `API_KEY_SECRET` only when neither scoped key matches), this is a second,
unguarded path to full `graph_admin` access.
**Fix sketch:** apply `check_api_key_secret` (or a shared subset — length + placeholder block) to
both fields via a `field_validator` conditioned on non-None.

### [L1-03] Admin-scoped `npc_ids`/`location_ids` request lists have no upper bound

Severity: LOW · Confidence: Confirmed

**Evidence:** `api/routes/admin/batch.py:28,38` (`GossipTickRequest.npc_ids`,
`EventTickRequest.location_ids`), `api/routes/admin/graph_admin.py:52` (`npc_ids`) — all
`list[str] = Field(default_factory=list)`, no `max_length`. Contrast with the same file's
`max_pairs: int = Field(default=20, ge=1, le=500)` (`batch.py:30`), which is capped, and with
`MAX_PLAYER_MESSAGE_CHARS`/`pagination.MAX_LIMIT`, which are the pattern CLAUDE.md's "input caps
at the API boundary" rule expects everywhere.
**Already known:** none found in `ISSUES.md`/`archive/ISSUES_RESOLVED.md`.
**Why it matters:** these routes require `SCOPE_GRAPH_ADMIN` (`_required_scope_for_path` on
`/v1/admin/*`), so this is not player-reachable — lowering severity to LOW. Still a boundary-cap
gap: a compromised or misused admin key could submit an arbitrarily large `npc_ids` list to
`run_tick`, which fans out per-id graph/LLM work with no ceiling.
**Fix sketch:** `Field(default_factory=list, max_length=200)` (or reuse `pagination.MAX_LIMIT`) on
all three fields.

### [L1-04] `is_public_path` treats `/setup` as a prefix match, not a route allow-list

Severity: LOW · Confidence: Suspected

**Evidence:** `auth/middleware_helpers.py:26,71-72`:
```python
SETUP_PATH_PREFIX = "/setup"
...
if path.startswith(SETUP_PATH_PREFIX):
    return env == "dev"
```
`setup.py:35` registers `router = APIRouter(prefix="/setup", ...)` with exactly three routes
(`/setup/validate`, `/setup/config` GET/POST), so today `startswith("/setup")` and "is one of the
three registered setup routes" happen to coincide. This is a prefix match, not a route-set check.
**Why it matters (Suspected — would need to be confirmed by adding a new route):** if a future
route is ever added under any path beginning with the literal string `/setup` but not intended to
be part of the wizard-exempt set (e.g. `/setup2/...` or a typo'd sibling router), it would
silently inherit the dev-only-auth-exempt behaviour with no route-registration-time signal. Same
shape of bug as `SETUP_PATH_PREFIX` being string-prefix rather than path-segment matching — `path
== "/setupx"` would NOT match (`startswith` requires the literal chars), but `path ==
"/setup-extra"` would.
**What would confirm it:** none currently reachable — no such route exists today. Flagging as a
narrow-the-check hardening item, not a live vulnerability.
**Fix sketch:** match `path == SETUP_PATH_PREFIX or path.startswith(f"{SETUP_PATH_PREFIX}/")`.
`DASHBOARD_PATH_PREFIX` at `middleware_helpers.py:73` has the identical prefix-only pattern and
would benefit from the same `/`-boundary fix.
